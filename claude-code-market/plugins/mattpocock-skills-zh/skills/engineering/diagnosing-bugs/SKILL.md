# 诊断缺陷

这是一套处理棘手缺陷的纪律。只有理由明确时才能跳过阶段。

探索代码库时，若存在 `CONTEXT.md`，先阅读它以建立相关模块的清晰心智模型，并检查所触及区域的 ADR。

## 脱敏

本 skill 会让你展示命令、输出和采集产物。**必须先移除所有密钥**——在原位置写入 `<REDACTED>`。让反馈循环从环境变量读取凭据，使凭据留在环境中，而不是出现在展示内容里。采集产物可能携带认证头；只引用真正承载诊断信号的行。

如果脱敏后的输出不足以诊断缺陷，应明确说明并询问用户。

## 阶段 1——建立反馈循环

**这就是本 skill 的核心。** 其他一切都只是机械步骤。只要你拥有一条针对_这个缺陷_会变红的**紧凑**通过/失败信号，就能找到原因；二分、假设检验和插桩都只是在使用这条信号。没有它，再久地盯着代码也无济于事。

在这里投入远高于其他阶段的精力。**要积极、要有创造力、拒绝放弃。**

### 构造方式——大致按以下顺序尝试

1. 在能够触达缺陷的任意接缝处编写**失败测试**——单元、集成或端到端测试。
2. 针对正在运行的开发服务器编写 **Curl / HTTP 脚本**。
3. 使用固定输入执行 **CLI 命令**，并把 stdout 与已知正确的快照比较。
4. 编写**无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，并断言 DOM、控制台或网络行为。
5. **重放采集到的 trace。** 把真实网络请求、payload 或事件日志保存到磁盘，再隔离地通过代码路径重放。
6. **一次性测试架。** 启动系统的最小子集（一个服务、mock 依赖），通过一次函数调用走过缺陷代码路径。
7. **属性测试 / fuzz 循环。** 如果缺陷表现为“有时输出错误”，运行 1000 个随机输入并寻找失败模式。
8. **二分测试架。** 如果缺陷出现在两个已知状态（commit、数据集、版本）之间，自动执行“在状态 X 启动、检查、重复”，以便运行 `git bisect run`。
9. **差分循环。** 让同一输入分别通过旧版本与新版本（或两种配置），再比较输出。
10. **HITL Bash 脚本。** 最后的手段。如果必须由人点击，就用 `scripts/hitl-loop.template.sh` 驱动_人_，让循环仍然结构化；采集到的输出再反馈给你。

建立正确的反馈循环，缺陷就已经修好 90%。

### 收紧循环

把循环当作产品。一旦有了_一条_循环，就继续**收紧**：

- 能否更快？（缓存设置、跳过无关初始化、缩小测试范围。）
- 信号能否更锐利？（断言具体症状，而不是“没有崩溃”。）
- 能否更确定？（固定时间、为 RNG 设种子、隔离文件系统、冻结网络。）

一条耗时 30 秒且不稳定的循环只比没有稍好；一条 2 秒、确定的循环才足够紧凑——它是调试的超能力。

### 非确定性缺陷

目标不是干净复现，而是获得**更高的复现率**。把触发动作循环 100 次、并行执行、增加压力、缩窄时序窗口、注入 sleep。复现率 50% 的 flaky 缺陷可以调试，1% 则不行——持续提高复现率，直到足以调试。

### 确实无法建立循环时

停下来明确说明。列出已经尝试的内容。向用户索取以下任一项：(a) 可复现环境的访问权；(b) 脱敏后的采集产物（HAR 文件、日志转储、core dump、带时间戳录屏）；或 (c) 添加临时生产插桩的许可。**没有循环，就不要继续提出假设。**

### 完成标准——一条能变红的紧凑循环

当循环既**紧凑**又**能变红**时，阶段 1 才算完成：你能指出**一条命令**——脚本路径、测试调用或 curl——已经**实际运行过至少一次**（展示脱敏后的调用和输出），并且满足：

- [ ] **能变红**——它走过真实缺陷代码路径，并断言用户报告的**精确症状**，因此会在这个缺陷上变红、修复后变绿。不能只是“运行不报错”——必须能_捕获这个具体缺陷_。
- [ ] **确定**——每次运行给出相同结论（对于 flaky 缺陷，则按前述方式固定一个较高复现率）。
- [ ] **快速**——以秒计，而不是分钟。
- [ ] **代理可运行**——可以无人值守运行；只有通过 `scripts/hitl-loop.template.sh` 才允许人工参与循环。

如果发现自己在这条命令存在之前就开始阅读代码、建立理论，**立即停下——直接跳到假设正是本 skill 要阻止的失败模式。** 没有能变红的命令，就不能进入阶段 2。

## 阶段 2——复现并最小化

运行循环，观察它变红——缺陷出现。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是碰巧发生在附近的另一个失败。缺陷找错，修复也会错。
- [ ] 失败能够多次复现（对于非确定性缺陷，则达到足以调试的高复现率）。
- [ ] 已经捕获精确症状（错误消息、错误输出或慢耗时），后续阶段才能验证修复确实解决了它。

### 最小化

循环变红后，把复现缩减成**仍会变红的最小场景**。每次只删除一个输入、调用方、配置、数据或步骤，并在每次删除后重新运行循环——只保留承载失败所必需的内容。

这样做的原因是：最小复现能缩小阶段 3 的假设空间（剩下的可疑活动部件更少），并在阶段 5 变成干净的回归测试。

当**每个剩余元素都不可或缺**时才算完成——删除其中任何一个，循环都会变绿。

完成复现和最小化之前不要继续。

## 阶段 3——提出假设

测试任何假设之前，先提出 **3–5 个按可能性排序的假设**。只提出一个假设会让你被第一个看似合理的想法锚定。

每个假设都必须**可证伪**：说明它作出的预测。

> 格式：“如果 <X> 是原因，那么改变 <Y> 会让缺陷消失，或改变 <Z> 会使缺陷加重。”

无法写出预测的假设只是感觉——删除或收紧它。

**测试前向用户展示排序列表。** 用户往往掌握能立刻改变排序的领域知识（“我们刚部署了与第 3 项有关的改动”），或知道哪些假设已经排除。这个检查点成本低、收益大。不要因此阻塞——用户不在线时按现有排序继续。

## 阶段 4——插桩

每个探针都必须对应阶段 3 的某项具体预测。**一次只改变一个变量。**

工具优先级：

1. 环境支持时使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界添加**定向日志**。
3. 永远不要“记录一切再 grep”。

给**每条调试日志**添加唯一前缀，例如 `[DEBUG-a4f2]`。最后只需搜索一次即可清理；无标签日志会存活，有标签日志必须删除。

**性能分支。** 对性能回退而言，日志通常是错误工具。应建立基线测量（计时测试架、`performance.now()`、性能分析器、查询计划），然后二分。先测量，再修复。

## 阶段 5——修复并添加回归测试

**修复之前**先写回归测试——但前提是存在**正确的接缝**。

正确接缝应让测试按照真实调用点中的样子，覆盖**实际缺陷模式**。如果唯一可用的接缝太浅（缺陷需要多个调用方，测试却只有一个；触发缺陷需要完整调用链，单元测试却无法复制），在那里写回归测试只会制造虚假信心。

**如果没有正确接缝，这本身就是发现。** 记录下来。代码库架构正在阻止缺陷被锁定；把它标记给下一阶段处理。

如果存在正确接缝：

1. 把最小复现转为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始、未最小化的场景重新运行阶段 1 的反馈循环。

## 阶段 6——清理与复盘

宣布完成前必须确认：

- [ ] 原始复现不再出现（重新运行阶段 1 的循环）。
- [ ] 回归测试通过（或已记录缺少接缝）。
- [ ] 已删除所有 `[DEBUG-...]` 插桩（使用 `grep` 等搜索工具查找该前缀）。
- [ ] 一次性原型已删除（或移到明确标注的调试位置）。
- [ ] commit 或 PR 信息说明了最终成立的假设——让下一位调试者能够学习。

**最后追问：什么能从源头避免这个缺陷？** 若答案涉及架构变化（没有良好测试接缝、调用方纠缠、隐藏耦合），应把具体发现交给 `/improve-codebase-architecture` skill。建议要在修复完成_之后_提出，而不是之前——现在掌握的信息比开始时更多。
