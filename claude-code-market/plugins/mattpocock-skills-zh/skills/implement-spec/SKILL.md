你已获得一份规格。它应有关联工单，用于描述如何实施这份规格。

应已提供 issue 跟踪器；如果没有，告知用户运行 `/setup-matt-pocock-skills`。

目标是在单一**集成分支**上实施整份规格，并按 issue 跟踪器的结项方式完成每张工单。

这些工单不是步骤列表，而是带阻塞关系的**任务图**。因此，任何时刻都会有一组可立即领取的工单，称为 **frontier**。

与子代理之间应保持稀疏通信，主要通过指向规格、工单、研究笔记和既有提交的**上下文指针**交流。不要重复指针已经提供的信息。

在条件允许时，让 **implementer 子代理**在后台运行，以取得最大并发度。

## 步骤

1. 阅读规格和工单，理解任务图。

2. （可选）使用 **exploration 子代理**完成工单所需的代码库或外部文档调查。确保该子代理能保存文件；它应把 Markdown 笔记保存在仓库外、所有后续子代理都能访问的目录中，使 **implementer 子代理**专注于实施而非调查。

3. 创建集成分支。如果 issue 跟踪器通过 PR 结项，或用户要求 PR，就在步骤 5 首次合并之后创建草稿 PR，标记为关闭规格 issue 及其工单；尚无领先于 main 的提交时无法创建 PR。

4. 使用 **implementer 子代理**实施每张工单，各自在自己的 worktree 和分支中工作。每个 implementer 子代理：
   - 开始前确认 worktree 基于集成分支；如果不是，则将其重置到集成分支；
   - 调用 Skill 工具并传入 `tdd`，构建该工单；
   - 报告完成前，将集成分支的最新提交合入自己的分支。

5. 每当一个 **implementer 子代理**完成，就使用 **merger 子代理**把它的工作合入集成分支。

6. 如果可用工单的 **frontier** 发生变化，就启动更多 **implementer 子代理**处理新工单，以取得最大并发度。

7. 全部工单完成后，调用 Skill 工具并传入 `code-review`，审查集成分支。使用单个 **implementer 子代理**修复代码审查提出的全部问题。

8. 如果存在草稿 PR，将其标记为可供审查。否则，按 issue 跟踪器的结项方式完成每张工单，并报告集成分支。

9. 清理所有 **implementer 子代理**的 worktree。
