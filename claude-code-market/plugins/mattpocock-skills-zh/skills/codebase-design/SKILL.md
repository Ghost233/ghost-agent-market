# 代码库设计

设计**深模块**：在干净接缝的小接口后隐藏大量行为，并通过该接口测试。凡是设计或重构代码，都应使用这里的语言和原则。目标是为调用者提供杠杆，为维护者提供局部性，为所有人提供可测试性。

## 术语表

严格使用以下术语——不要用“组件”“服务”“API”或“边界”替代。一致的语言正是重点所在。

**模块（Module）**——任何拥有接口和实现的事物。刻意不限定规模：可以是函数、类、包或跨层切片。_避免使用_：单元、组件、服务。

**接口（Interface）**——调用者正确使用模块必须知道的一切：不仅包括类型签名，还包括不变量、顺序约束、错误模式、必需配置和性能特征。_避免使用_：API、签名（范围太窄，只指类型层面的表面）。

**实现（Implementation）**——模块内部的代码主体。它与**适配器**不同：一个事物可以是实现很大的小型适配器（Postgres 仓库），也可以是实现很小的大型适配器（内存 fake）。讨论接缝时使用“适配器”，其他情形使用“实现”。

**深度（Depth）**——接口处的杠杆：调用者（或测试）每学习一单位接口，能够驱动多少行为。小接口后包含大量行为的模块是**深**模块；接口与实现几乎同样复杂的模块是**浅**模块。

**接缝（Seam）** _（Michael Feathers）_——无需在某处编辑代码，就能在该处改变行为的位置；也就是模块接口所在的_位置_。把接缝放在哪里是一项独立的设计决策，与接缝后放什么不同。_避免使用_：边界（它与 DDD 的限界上下文含义重叠）。

**适配器（Adapter）**——在接缝处满足接口的具体事物。它描述的是_角色_（填补哪个位置），而不是实质（内部是什么）。

**杠杆（Leverage）**——调用者从深度获得的收益：每学习一单位接口，获得更多能力。一个实现会在 N 个调用点和 M 个测试中持续产生回报。

**局部性（Locality）**——维护者从深度获得的收益：变更、缺陷、知识和验证集中在一处，而不是散布到各个调用者。修复一次，处处生效。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│       深实现        │  ← 隐藏复杂逻辑
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（应避免）：

```
┌─────────────────────────────────┐
│             大接口              │  ← 方法多，参数复杂
├─────────────────────────────────┤
│             薄实现              │  ← 只做透传
└─────────────────────────────────┘
```

设计接口时，询问：

- 能否减少方法数量？
- 能否简化参数？
- 能否在内部隐藏更多复杂性？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小型、可 mock、可替换的部件组成——它们只是不属于接口。模块既可以拥有实现私有、供自身测试使用的**内部接缝**，也可以在接口处拥有**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂性随之消失，它只是透传层；如果复杂性重新散布到 N 个调用者，说明这个模块确有价值。
- **接口就是测试表面。** 调用者与测试跨越同一接缝。如果你想越过接口进行测试，模块的形状很可能不正确。
- **一个适配器意味着假想的接缝，两个适配器意味着真实的接缝。** 除非确实有事物会在接缝两侧发生变化，否则不要引入接缝。

## 为可测试性设计

良好的接口让测试自然发生：

1. **接收依赖，不要在内部创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **保持较小的表面积。** 方法越少，需要的测试越少；参数越少，测试设置越简单。

## 关系

- 一个**模块**恰好拥有一个**接口**（呈现给调用者和测试的表面）。
- **深度**是**模块**的属性，根据其**接口**衡量。
- **接缝**是**模块**的**接口**所在的位置。
- **适配器**位于**接缝**处并满足**接口**。
- **深度**为调用者产生**杠杆**，为维护者产生**局部性**。

## 不采用的说法

- **把深度定义为实现行数与接口行数之比**（Ousterhout）：这会奖励填充实现。这里把深度定义为杠杆。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的公共方法**：范围太窄——这里的接口包括调用者必须知道的每一项事实。
- **“边界”**：它与 DDD 的限界上下文含义重叠。应使用**接缝**或**接口**。
