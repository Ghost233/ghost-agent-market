# 转为工单

把计划、规格或对话拆成一组**工单**：每张都是曳光弹式垂直切片，并明确声明**阻塞它**的其他工单。

应已提供 issue tracker 与分诊标签词汇；若没有，运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

优先使用当前对话已有信息。用户传入规格路径、issue 编号或 URL 时，获取并完整阅读正文与评论。

### 2. 探索代码库（可选）

若还未探索代码库，应先了解当前实现。工单标题和描述使用项目领域词汇表中的语言，并遵守相关区域的 ADR。

寻找能让后续实现更容易的预重构机会：“先让改动变容易，再完成容易的改动。”

### 3. 起草垂直切片

把工作拆成**曳光弹式**工单。

<vertical-slice-rules>

- 每个切片都以窄而完整的路径贯穿所有相关层（schema、API、UI、测试），不能只横切某一层。
- 每个切片完成后都能单独演示或验证。
- 每个切片都能放进一个全新的上下文窗口完成。
- 需要的预重构应先完成。

</vertical-slice-rules>

为每张工单声明**阻塞边**：开始它之前必须完成的其他工单。没有阻塞项的工单可立即开始。

**大范围重构是垂直切片的例外。** **大范围重构**是一次机械改动——例如重命名列或重设共享符号类型——其**影响范围**横跨整个代码库，一次修改会破坏大量调用点，无法让任何垂直切片独立保持绿色。不要强行把它做成曳光弹，而应采用**扩展—收缩**序列。先扩展：在旧形式旁添加新形式，确保现有内容不坏。再按影响范围分批迁移调用点（例如按 package 或目录分组）；每批一张工单，并被扩展工单阻塞。旧形式仍然存在，因此每批之后 CI 都保持绿色。最后收缩：所有迁移批次完成、没有旧调用方后删除旧形式；该工单被所有迁移工单阻塞。如果连迁移批次也无法独立保持绿色，仍保留此顺序，但让它们共享一个集成分支，并共同阻塞最后的“集成并验证”工单——只在最终工单承诺绿色。

### 4. 向用户确认

用编号列表展示拆分方案。每张工单都列出：

- **标题**：简短描述。
- **被什么阻塞**：开始前必须完成的工单；没有则明确说明。
- **交付内容**：该工单打通的端到端行为。

询问用户：

- 粒度是否合适（太粗或太细）？
- 阻塞边是否正确——每张工单是否只依赖真正构成门槛的工单？
- 是否应合并某些工单，或继续拆分？

迭代到用户批准为止。

### 5. 发布到已配置的 tracker

发布批准后的工单。具体形式由 `/setup-matt-pocock-skills` 配置的 tracker 决定；工单内容相同，只有阻塞边的表达不同：

- **本地文件**：在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 为每张工单写一个文件，从 `01` 开始按依赖顺序编号，阻塞项在前。“Blocked by”列出依赖的编号和标题。严格使用下方模板；每个文件只放一张工单，不能合并成一个文件。
- **真实 issue tracker（GitHub、Linear 等）**：按依赖顺序逐张发布，先创建阻塞项，使后续工单能引用真实标识。平台支持时使用原生 blocking/sub-issue 关系，否则在 “Blocked by” 中列出阻塞 issue。除非另有要求，添加 `ready-for-agent` 分诊标签；这些工单本来就应能被代理领取。

工作从 **frontier** 开始，即所有阻塞项均已完成的工单。纯线性链按从上到下执行。

不要关闭或修改父 issue。
