# ADR 格式

ADR 保存在 `docs/adr/` 中，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

按需创建 `docs/adr/` 目录——只有在需要第一项 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、作出了什么决定、为什么。}
```

完整格式仅此而已。ADR 可以只有一个段落。它的价值在于记录_作出了决策_以及_为什么_——而不是填满各个章节。

## 可选章节

仅在确有价值时加入。大多数 ADR 都不需要这些章节。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——重新审视决策时有用；
- **Considered Options**——只有被拒绝的替代方案值得记住时使用；
- **Consequences**——只有需要指出不显而易见的下游影响时使用。

## 编号

扫描 `docs/adr/` 中现有的最大编号，并加一。

## 何时建议 ADR

以下三项必须全部成立：

1. **难以逆转**——以后改变主意的成本显著；
2. **缺少背景会令人意外**——未来读者看到代码会疑惑：“他们到底为什么这样做？”；
3. **源于真实取舍**——确实存在替代方案，并因具体理由选择了其中一个。

容易逆转的决策应跳过——到时直接逆转即可。若并不令人意外，就没人会追问原因。若不存在真正的替代方案，除了“我们选择了显而易见的做法”之外就没有可记录的内容。

### 哪些内容适合记录

- **架构形状。** “我们使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 与 Billing 通过领域事件通信，而不是同步 HTTP。”
- **会产生锁定成本的技术选择。** 数据库、消息总线、认证提供商、部署目标。不是每个库都要记录——只记录那些需要一个季度才能替换的选择。
- **边界和范围决策。** “Customer 数据归 Customer 上下文所有，其他上下文只通过 ID 引用。”明确的“不做什么”与“做什么”同样有价值。
- **刻意偏离显而易见的路径。** “因为 X，我们使用手写 SQL 而不是 ORM。”只要合理的读者可能会假定相反做法，就应记录。这能阻止下一位工程师“修复”一个刻意作出的决定。
- **代码中不可见的约束。** “由于合规要求，我们不能使用 AWS。”“由于合作方 API 契约，响应时间必须低于 200ms。”
- **拒绝理由不显而易见的替代方案。** 如果你考虑过 GraphQL，却因细微原因选择 REST，应当记录——否则六个月后还会有人再次建议 GraphQL。
