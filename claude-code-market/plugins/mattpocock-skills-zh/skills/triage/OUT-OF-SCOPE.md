# 范围外知识库

仓库中的 `.out-of-scope/` 保存被拒绝功能请求的持久记录，用于：

1. **组织记忆**：issue 关闭后仍保留拒绝理由。
2. **去重**：新 issue 与既往拒绝相似时，直接指出原决定，避免重新争论。

## 目录结构

```text
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件；请求同一内容的多个 issue 归入同一文件。

## 文件格式

使用轻松、易读的短设计文档风格。可用段落、代码样例和例子，让首次阅读者也能理解决定。

````markdown
# 深色模式

本项目不支持深色模式或面向用户的主题切换。

## 为什么不在范围内

渲染流水线假设只有 `ThemeConfig` 定义的一套调色板。支持多主题需要：

- 包裹整个组件树的主题 context provider
- 每个组件感知主题的样式解析
- 保存用户主题偏好的持久层

这是重大的架构改动，与项目专注内容创作的目标不一致。
主题化应由嵌入或重新分发输出的下游消费者负责。

```ts
// 当前 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单套调色板，构建时解析
  fonts: FontStack;
}
```

## 既往请求

- #42 — “添加深色模式”
- #87 — “用于无障碍的夜间主题”
- #134 — “深色主题选项”
````

### 文件命名

使用简短、描述性的 kebab-case 概念名，例如 `dark-mode.md`、`plugin-system.md`、`graphql-api.md`。浏览目录时无需打开文件也应知道拒绝了什么。

### 编写理由

理由必须有实质内容，不能只是“我们不想要”。良好理由应引用：

- 项目范围或理念，例如“项目专注 X，主题化属于下游责任”。
- 技术约束，例如“支持它需要 Y，而 Y 与 Z 架构冲突”。
- 战略决定，例如“我们选择 A 而不是 B，因为……”。

理由必须经得起时间变化。不要引用“最近太忙”等临时情况；那是延期，不是真正拒绝。

## 何时检查 `.out-of-scope/`

分诊收集上下文时，阅读 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配现有范围外概念。
- 按概念相似性而非关键词匹配；“夜间主题”应匹配 `dark-mode.md`。
- 若匹配，向维护者说明：“这与 `.out-of-scope/dark-mode.md` 相似；我们之前因 [理由] 拒绝过。现在仍坚持这个决定吗？”

维护者可以：

- **确认**：把新 issue 追加到既有文件的“既往请求”，然后关闭。
- **重新考虑**：删除或更新范围外文件，让 issue 进入正常分诊。
- **不同意匹配**：两项相关但不同，继续正常分诊。

## 何时写入 `.out-of-scope/`

只有 **enhancement**（不是 bug）因被拒绝而标为 `wontfix` 时才写入。被拒绝的 enhancement PR 与 issue 相同，也要记录，避免同一请求以后以新代码形式返回。

不要因内容**已经实现**而以 `wontfix` 关闭时写入。那是已构建的功能，不是被拒绝的功能；错误记录会污染后续去重。关闭评论应直接指出实现位置。

流程：

1. 维护者决定功能请求不在范围内。
2. 检查是否已有匹配的 `.out-of-scope/` 文件。
3. 若有，把新 issue 追加到“既往请求”。
4. 若无，用概念名创建文件，写入决定、理由和第一条既往请求。
5. 在 issue 评论中解释决定并提到该文件。
6. 添加 `wontfix` 标签并关闭 issue。

## 更新或删除范围外文件

维护者改变既往决定时：

- 删除 `.out-of-scope/` 中对应文件。
- 无需重新打开旧 issue；它们是历史记录。
- 触发重新考虑的新 issue 进入正常分诊。
