# 编写代理简报

代理简报是在 GitHub issue 或 PR 转为 `ready-for-agent` 时发布的一条结构化评论。它是 AFK 代理工作的权威规格。原始正文和讨论只是上下文——代理简报才是契约。

简报说明**代理应该完成什么**，这个范围覆盖两种入口：对于 issue，是从零构建改动；对于 PR，是对_现有 diff_ 还需要做什么——完成实现、补齐缺口、处理评审意见。两种情形遵循相同原则；下方 PR 示例会展示其中的区别。

## 原则

### 持久性优先于精确性

issue 可能在 `ready-for-agent` 停留数天或数周，期间代码库会发生变化。编写简报时，要让它在文件被重命名、移动或重构后仍然有用。

- **应当**描述接口、类型和行为契约；
- **应当**指出代理要寻找或修改的具体类型、函数签名或配置形状；
- **不要**引用文件路径——它们会过时；
- **不要**引用行号；
- **不要**假设当前实现结构会保持不变。

### 描述行为，不规定过程

描述系统**应该做什么**，而不是**如何**实现。代理会重新探索代码库，并自行作出实现决策。

- **好：** “`SkillConfig` 类型应接受一个类型为 `CronExpression` 的可选 `schedule` 字段。”
- **差：** “打开 src/types/skill.ts，在第 42 行添加 schedule 字段。”
- **好：** “用户无参数运行 `/triage` 时，应看到需要注意的 issue 摘要。”
- **差：** “在主 handler 函数中添加 switch 语句。”

### 完整的验收标准

代理需要知道何时算完成。每份代理简报都必须包含具体、可测试的验收标准。每项标准都应能独立验证。

- **好：** “运行 `gh issue list --label needs-triage` 会返回已经完成初始分类的 issue。”
- **差：** “分诊应该正确工作。”

### 明确范围边界

说明哪些内容不在范围内。这能防止代理过度打磨，或对邻近功能擅自作出假设。

## 模板

```markdown
## 代理简报

**类别：** bug / enhancement
**摘要：** 一行说明要完成什么

**当前行为：**
描述现在发生什么。对于 bug，这里写损坏的行为。
对于 enhancement，这里写功能建立其上的现状。

**期望行为：**
描述代理完成工作后应该发生什么。
明确说明边缘情况和错误条件。

**关键接口：**
- `TypeName`：需要改变什么，以及原因
- `functionName()` 的返回类型：当前返回什么，期望返回什么
- 配置形状：需要哪些新配置项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**范围外：**
- 本 issue 不应改变或处理的内容
- 看似相关、但应单独处理的邻近功能
```

## 示例

### 良好的代理简报（bug）

```markdown
## 代理简报

**类别：** bug
**摘要：** Skill 描述在单词中间截断，产生破损输出

**当前行为：**
skill 描述超过 1024 个字符时，会精确截到第 1024 个字符，
不考虑单词边界。这会让描述停在单词中间
（例如 “Use when the user wants to confi”）。

**期望行为：**
截断位置应是 1024 个字符之前的最后一个单词边界，
并追加 “...” 表示内容已截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段——不需要改变类型，
  但填充该字段的验证/处理逻辑必须尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取 description 的函数

**验收标准：**
- [ ] 少于 1024 个字符的描述保持不变
- [ ] 超过 1024 个字符的描述在限制前最后一个单词边界截断
- [ ] 截断后的描述以 “...” 结尾
- [ ] 包含 “...” 的总长度不超过 1024 个字符

**范围外：**
- 改变 1024 个字符的限制本身
- 支持多行描述
```

### 良好的代理简报（enhancement）

```markdown
## 代理简报

**类别：** enhancement
**摘要：** 添加 `.out-of-scope/` 目录支持，用于跟踪被拒绝的功能请求

**当前行为：**
功能请求被拒绝时，issue 会带 `wontfix` 标签和一条评论关闭。
目前没有持久记录保存这项决定或其理由。
未来出现相似请求时，维护者必须记得或搜索之前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
其中包含决定、理由，以及提出该功能的所有 issue 链接。
分诊新 issue 时，应检查这些文件是否存在匹配项。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式——每个文件都应包含
  `# 概念名` 标题、`**决定：**` 行、`**理由：**` 行，
  以及含 issue 链接的 `**既往请求：**` 列表
- 分诊流程应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似性匹配传入的 issue

**验收标准：**
- [ ] 以 wontfix 关闭 enhancement 时，会在 `.out-of-scope/` 中创建或更新文件
- [ ] 文件包含决定、理由和已关闭 issue 的链接
- [ ] 若已经存在匹配的 `.out-of-scope/` 文件，
      则把新 issue 追加到其“既往请求”列表，而不是创建重复文件
- [ ] 分诊期间会检查现有 `.out-of-scope/` 文件，
      并在新 issue 匹配既往拒绝时指出该记录

**范围外：**
- 自动匹配（由人确认是否匹配）
- 重新打开以前被拒绝的功能
- bug 报告（只有被拒绝的 enhancement 才进入 `.out-of-scope/`）
```

### 良好的代理简报（PR）

对于 PR，“当前行为”描述 diff 当前的状态；简报要求代理完成或修复它，而不是从零构建。

```markdown
## 代理简报

**类别：** enhancement
**摘要：** 完成贡献者为 `triage list` 添加的 `--json` 输出选项

**当前行为：**
PR 添加了一个 `--json` 选项，把 issue 列表序列化为 JSON。
正常路径已经可用，diff 也符合项目的命令结构。
但仍有两个缺口：错误仍以人类可读文本输出（不是 JSON），
而且新选项没有测试覆盖。

**期望行为：**
使用 `--json` 时，所有输出——包括错误——都应在 stdout 上成为格式正确的 JSON，
命令退出码保持不变。未提供该选项时，现有人类可读输出保持不变。

**关键接口：**
- 使用 `--json` 时，命令错误路径应输出 `{ "error": string }`，
  而不是纯文本错误
- 复用 PR 已添加的序列化器，不要引入第二套

**验收标准：**
- [ ] `triage list --json` 在成功和错误情形下都输出有效 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 测试覆盖 `--json` 的成功输出和一个错误情形
- [ ] 默认（非 JSON）输出逐字节保持不变

**范围外：**
- 为其他命令添加 `--json`
- 改变 PR 已定义的成功载荷 JSON 形状
```

### 糟糕的代理简报

```markdown
## 代理简报

**摘要：** 修复分诊 bug

**要做什么：**
分诊坏了。查看主文件并修复。
第 150 行附近的函数有问题。

**要修改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这份简报很差，因为：

- 没有类别；
- 描述含糊（“分诊坏了”）；
- 引用了会过时的文件路径和行号；
- 没有验收标准；
- 没有范围边界；
- 没有说明当前行为与期望行为。
