# 维护功能知识

显式调用时给出功能、所属仓库和阶段：`讨论后整理` 或 `验收后更新`。本 skill 只维护知识文档和必要索引；不实施业务代码、自动提交或发布。

```text
$compile-feature-knowledge <仓库> <功能>，讨论后整理刚才已确认的决策。
$compile-feature-knowledge <仓库> <功能>，验收后根据本次改动和验证结果更新现状。
```

## 定位与查询

1. 读取目标仓库的 `AGENTS.md`、`CLAUDE.md`、领域文档和已有功能档案，遵循已有目录约定。没有现成约定时，首次建立于 `docs/knowledge/features/<功能标识>.md`，并在 `docs/knowledge/` 下维护 OKF bundle。
2. 同一功能始终维护同一稳定路径；复用 `CONTEXT.md`、ADR、spec、合同、测试和 Git 历史，不按讨论日期新建摘要。
3. 需要历史结论时，使用当前平台提供的只读探索能力查询该功能档案与其来源，必要时再追溯代码和 Git。Codex 可使用 `explorer`，其他平台使用等价的只读子智能体。要求它一次性返回当前结论、关键约束与理由、已替代方案、冲突或缺口，以及具体出处。主线程等待结果后再作依赖这些历史的决定。
4. 重要结论若只存在于当前聊天，记录确认日期、结论、理由和“依据本次用户确认”；不要伪造聊天链接或复制完整聊天。

## 讨论后整理

- 只写入用户已确认的目标、约束、取舍和理由。
- 新方案进入“已采纳但待实施的变更”，并链接 spec 或 ADR。讨论确认不等于当前代码已经实现。
- 保留已有“当前行为”；只有有代码或验证证据的事实才能写入该章节。
- 新方案替代旧方案时标明替代关系和来源；尚未实施时保留旧行为描述。

## 验收后更新

- 对照本次 diff、spec 验收条件、测试和审查证据更新“当前行为”和约束。
- 记录验证覆盖范围、版本或 diff、命令与结果；源码核对、测试通过和线上生效分别表述。
- 只移除已落实的待实施事项。部分完成、未验证或与设计不一致的内容保留为限制、偏差或待验证项。
- 旧验证不能为实质变更后的内容背书。没有足够证据时保留缺口，不补写结论。

## 文档内容

按需维护以下章节，空章节不必创建：

- 目标与边界
- 当前行为与关键约束
- 设计理由
- 已采纳但待实施的变更
- 已知限制与设计偏差
- 代码、合同与测试入口
- 验证依据

功能档案负责说明如何维护该功能；协议字段以合同为准，已实现行为以代码和运行证据为准，采纳意图以确认和 ADR 为准。出现冲突时分别记录，不按文件日期自行裁决。

## OKF 0.2

- 功能概念使用 `type: Feature`，并带 `title`、单句 `description`；按需使用 `tags`。`status` 表示文档生命周期：首次整理用 `draft`，可供消费用 `stable`，保留历史用 `deprecated`，不表示代码是否上线。
- `sources` 为每份外部依据设置稳定 `id` 和真实 `resource`；关键结论以同名脚注归因。普通相对路径按当前文档解析，`/` 开头的链接按 OKF bundle 根解析。
- 仅在实质修改时写入真实的 `generated.by` 和带时区的 `generated.at`。`verified` 只记录实际核验当前文档的人或过程；局部测试不能为全文背书。实质内容改变后，移除不再适用的验证标记，重新核验后再添加。
- 只有存在实际复核期限时才填写 `stale_after`。关联代码、合同或决策变化时重新检查文档。
- `index.md` 和 `log.md` 是保留文件名。bundle 根 `index.md` 可声明 `okf_version: "0.2"`；其他 `index.md` 不带 frontmatter。首次创建功能档案时按需建立或更新索引。

完成前检查 frontmatter 可解析、来源和脚注 ID 对应、受影响索引链接正确，并报告更新内容、验证证据和保留缺口。格式正确只代表结构正确，不代表业务事实已核验。
