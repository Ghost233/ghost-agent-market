# 工单粒度检查

在实施前判断本次任务的工单是否足够小。默认识别当前对话中的任务，无需提供 issue 编号；明确指定对象时以用户指定范围为准。合适的工单保持原样，过大的工单交给当前安装的 `mattpocock-skills-zh` 中的 `to-tickets` 继续拆分。本 skill 是独立的检查入口，不启动实施、测试、提交或交付。

## 1. 识别本次任务并列出检查项

主代理先依据当前对话中仍有效的用户目标、已确认决定和最新范围变更识别本次任务，复用明确关联的规格、父 issue、计划和执行记录。上下文已有依据时直接继续，不再要求用户提供编号或重新确认同一范围。

“继续”或状态询问沿用原目标；多个工单明确属于同一目标时一并检查，无需让用户逐个指定。

从这些来源读取正文、相关评论中的已确认变更、子项和阻塞关系；缺少位置时按仓库检索规则定向查找。检查清单只包含与本次任务有依据关联的未完成叶子工单和未覆盖范围，不扫描全仓所有开放 issue，也不按最近更新时间猜测对象。多个独立任务仍无法区分时，只补问选择哪一项。

已有子项时复用划分，父项只用于范围和覆盖核对。没有正式 issue 时，按当前任务已有计划条目或已确认要求列出工作项，保留来源，不虚构工单编号或父子关系。

无法识别有效任务或无法确定剩余范围时，只补问本次目标或资料来源。只有已识别任务并核实没有未完成范围时，才说明没有待检查项并结束；上下文缺失不算检查完成。

进行中的工单保留已完成工作和有效证据，只评估剩余范围。记录当前执行者、仍在执行的范围和交接状态。尚在执行且未确认交还的范围只给出拆分建议，不发布新子项，避免重复领取。

先简短展示识别到的任务、来源、检查项和排除的已完成范围。该说明用于让用户纠正识别结果，有明确依据时无需等待新的批准。

**完成标准：** 每个检查项有来源，原要求、剩余范围、已有划分和直接依赖可追溯；歧义已明确，不把其他任务混入清单。

## 2. 用子代理逐项检查

每个检查项分别交给一个子代理分析；相互独立的项按宿主并发限制分批运行，可复用空闲子代理逐项处理。主代理先完成对象识别和来源定位，子代理负责粒度判断，不重复扫描整个任务。

每次派发提供：本次任务摘要、分配的检查项及来源、适用的父项要求、已有子项和证据、直接依赖与当前执行归属。明确子代理只读分析这一项，不创建或修改工单、不调用 `to-tickets`、不启动实施。要求返回结论、支持依据、建议切口或缺失决定、承接的验收要求和依赖。

子代理依据以下问题判断，并引用工单条款或实际证据：

- **交付结果：** 是否混合了能分别交付的行为、准备工作或调查决定？把“全部支持”“完整恢复”等表述展开到实际承诺。
- **验收边界：** 能否说明相关输入类别、允许或拒绝的结果，以及通过什么公共入口验证？实现和测试可以一起补齐，不要求新测试已存在。
- **依赖与未知：** 是否要先解决会改变业务行为、跨仓协议、权限或验证方式的决定？独立前置工作可以另列，信息不足不能直接当作工单过大。
- **拆分价值：** 拆开后是否各有可使用、可独立验证的结果？同一行为的实现、回归测试和验证留在一项；跨文件或跨层本身不构成拆分理由。

文件数、估计工时、上下文长度和长测试只作线索。用有限的正常、拒绝或恢复场景说明承诺，不枚举所有组合，也不通过减少场景取消父项要求。采用上游已有的大范围重构处理方式，不强迫机械迁移成为独立业务切片。

代码证据只查到足以判断边界，遵循仓库检索规则。普通代码定位和实现选择由实施者解决。主代理沿原子代理句柄等待结果；失败或未返回的项标记未完成，保留其他项结果，不重跑整批。宿主无子代理能力时说明限制，改由主代理逐项检查，不声称已经委派。

**完成标准：** 每个检查项都有可核对的报告或明确的未完成原因；没有把超时、缺少证据或未检查记为粒度合适。

## 3. 主代理汇总结论

汇总各项报告，核对建议是否重复、冲突或漏掉父项要求，确认跨项依赖和正在执行的范围。子代理分歧按原要求和证据解决，缺少业务决定时才交用户判断。不要直接把多份子代理建议拼成新的工单清单。

对每个已完成检查的项输出以下一种结论，并附来源、依据和下一动作；未完成检查另列，不推断为通过：

| 结论 | 下一步 |
| --- | --- |
| 粒度合适 | 说明结果和验收边界；保持原划分，结束该项检查。另列未完成依赖，粒度合适不等于可立即领取。 |
| 需要细分 | 列出可独立交付的范围，准备下述拆分简报，衔接 `to-tickets`。 |
| 信息不足 | 指出哪项缺失决定会影响划分，先查已有材料；必须由用户决定时集中提问，暂不发布猜测出的子项。 |

已确认范围和判断依据未变化时复用结论并注明来源。真实的新承诺、新依赖或验证边界变化时，只让相关子代理复查受影响项。

**完成标准：** 汇总覆盖完整检查清单，结论有依据，重复范围和依赖已核对，阻塞与粒度分开，下一动作明确。

## 4. 衔接 to-tickets

由主代理统一衔接，子代理只返回分析。仅对“需要细分”的范围按原 issue 分组准备简短交接；没有正式 issue 时，以已确认的规格、计划或当前对话作为来源：

- 来源及要求的引用、已确认的目标和非目标；有原 issue 时明确其父项身份。
- 现有子项、已完成部分、有效结果，以及当前执行者、仍在执行的范围和交接状态。
- 建议的子项交付结果、阻塞关系和验证方式。
- 原验收条款分别由哪些已有或拟建子项承担；跨子项的集成验收也要有明确归属。

定位并读取当前安装的 `to-tickets`，通过宿主支持的 skill 调用方式传入简报。沿用它的 tracker 配置、垂直切片、确认和发布流程，不复制另一套拆票实现。要求其在确认方案前核对覆盖与粒度；草稿仍过大时修订草稿，不为凑固定层数重复发布。

`to-tickets` 可能只允许用户显式调用。宿主限制调用或依赖未安装时，保留已完成的判断与简报，说明具体限制及下一动作；显式入口为 Codex 的 `$to-tickets` 或 Claude Code 的 `/mattpocock-skills-zh:to-tickets`。调用未发生时不报告已调用。

拆分方案的确认和发布沿用现有授权；已明确批准且仍适用的方案不重复询问。仅要求检查时止于判断和简报，不自动发布。保持原需求、业务断言及强制门禁，不把父项的整体完成等同于子项局部完成。

**完成标准：** 报告真实状态：检查完成、拆分待确认、待显式调用或工单已发布。已发布时核对适用的父子关系、阻塞边和要求覆盖，给出工单引用与下一批可领取叶子；不关闭或修改父 issue。
