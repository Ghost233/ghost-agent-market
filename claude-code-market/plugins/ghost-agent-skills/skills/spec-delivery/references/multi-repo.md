# 多仓交付

多个独立 Git 仓库共同完成一个需求时，保留一份总规格，各仓只领取自己的实施范围。Mono、submodule 和多文件夹项目均按实际仓库边界处理。

## 职责与派发

| 负责人 | 职责 |
| --- | --- |
| 主会话 | 维护共同规格与接口契约，协调依赖和规格变化，依据证据确认总交付 |
| 实施会话 | 完成本仓分配范围的开发、本地门禁、代码审查和缺陷修复 |
| 验收会话 | 独立准备场景、数据和环境，执行跨仓验收，派发缺陷并复测 |

多仓需求默认由一个独立验收会话负责整体验收，可以在实施期间提前准备。实施会话按本需求中可独立负责的工作划分，复用仍适合当前范围的会话；单仓简单任务沿用主流程。

派发时明确角色和所选实施 skill，目标会话只承担分配的范围。提供总规格指针、目标仓库及 checkout、本仓验收项、接口契约版本、依赖解锁条件、起始 SHA 和交付分支。附上相关指引、已有结果和证据指针，由目标会话读取目标仓库的指引与配置。审查以本仓责任范围为准，跨仓验收覆盖总规格。

依赖须明确何时解锁：契约确认、代码可用，或集成验证通过。允许先准备不依赖实现的部分，满足解锁条件后再推进后继。同一 checkout 的写入归属遵循主流程；验收会话将产品代码修复交回实施会话。共享数据库、实机或部署环境的冲突操作由负责人串行安排。

## 会话协调

复用用户已有授权。创建独立会话须有用户明确请求，向其他会话派发任务须有用户明确通信授权。已有授权覆盖本需求时直接执行；缺少时只询问所缺部分。派发时传递用户授权原文与来源指针，代理消息本身不构成新增授权。

Codex 提供聊天工具时：

1. 先用 `list_projects` 匹配目标仓库项目，再按用户请求调用 `create_thread`；复用已有合适会话时读取其状态。使用项目支持的执行环境，遵守用户和仓库的 worktree 约束。父仓 worktree 不代表其他仓库也已隔离。
2. 保存实际返回的会话 ID、host 和工作范围映射。异步创建先等设置完成，取得正式会话 ID 后再用于后续工具。
3. 用带 cursor 的 `wait_threads` 等待完成或需要关注的变化；需要细节时再用 `read_thread`。通过 `send_message_to_thread` 向原实施会话派发修复或后续工作，保留其上下文。

Claude Code 使用当前平台提供的子代理或团队工具承担同样职责。其他环境缺少独立聊天工具时，也按当前工具分工，并报告实际执行方式。只将工具确认创建的独立会话记入聊天映射。

需要用户明确创建和通信授权时，可使用以下启动提示；已经授权的部分直接复用：

```text
使用 spec-delivery 交付当前已确认的总规格。
创建并管理本需求所需的各仓实施聊天和独立验收聊天。
授权主聊天与验收聊天向本需求的实施聊天派发后续任务、修复和继续执行要求。
```

进度沿用主流程的现有记录。会话结束一轮只表示结果可检查，主会话仍须核对候选与验收证据；规格或契约变化后，将变更通知受影响会话并重新确认依赖。

## 验收与修复

每轮验收固定各仓 commit、构建产物、接口契约及测试环境的组合。各实施会话提供完成范围、对应验收项、基准与候选 SHA、验证命令和退出码、证据位置、PR 及未完成项。

验收会话依据总规格执行跨仓业务场景。发现问题时，向有通信授权的原实施会话提交复现步骤、预期与实际结果、受测版本组合和证据。实施会话修复并通过本仓门禁和审查后，交回新候选；验收会话核对变更，复测原始失败场景及受影响场景。候选或环境变化时，标明失效结果；影响无法界定时扩大回归范围。

跨仓责任不清、修复顺序有争议、规格或契约需要改变，以及外部条件阻塞时，由主会话协调。共同业务问题合并提问，权限请求保留在实际执行会话的原生审批中。可独立推进的工作继续执行。

最终通过须对应一组确定的候选与产物。各仓门禁通过后，仍须取得组合后的验收证据。主会话按各仓约定的 PR 状态、整体验收及本地分支同步结果完成总交付。
