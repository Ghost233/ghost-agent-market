# Spec 完整交付

调用：Codex 用 `/goal $spec-delivery`，Claude Code 用 `/ghost-agent-skills:spec-delivery`。复用当前对话的 spec 和授权；缺少必要信息才提问。用户要求 goal 且平台支持时，建立或沿用对应 goal。

读取当前安装的 `mattpocock-skills-zh:implement-spec`、`mattpocock-skills-zh:code-review`、`mattpocock-skills-zh:retro`，遵循它们及其依赖。实施方式由 `implement-spec` 定义；审查方法、角色与报告格式由 `code-review` 定义。本 skill 负责调用衔接、结果复用与交付条件。

1. **固定阶段验收。** 确定 spec、工单、阶段及总交付的起始 SHA、验收条件、项目现有检查命令及分支流向：阶段 PR → 集成分支，总 PR → 目标分支。两者须分离，PR 只包含本次范围内的变更。需要真实服务或实机时，先验证最小真实路径可执行；缺口记录证据、责任人、解锁条件和下一动作。保留原规格，新增要求单独明确归属。
2. **沿用 Matt 实施。** 按 `implement-spec` 执行任务图、TDD、实现者与 merger 分工，明确文件归属。同阶段后继等待前置工单验收并进入阶段候选；跨阶段后继等待前置阶段通过审查并集成。共用 checkout 时 Git 操作串行。调用前说明：本阶段 PR 的最终 ready 与 worktree 清理由本 skill 在阶段验收后处理。
3. **承接阶段审查。** 沿用 `implement-spec` 的首审与集中修复结果，随后执行 `retro`、修复本次交付范围内已确认的 P0/P1/P2，再进入 `code-review` 复审。各次审查按下方调用约定执行。修复后的复审不自动重启整轮复盘，新证据表明复盘结论失效时再补对应部分。
4. **集中关闭发现。** 同类发现交给同一个修复实现者。同一类别两轮修复后仍未关闭，先使用 `diagnosing-bugs` 建立能区分原因的定点反馈，补齐有限的输入分类与成对边界，再继续修改。保留未完成状态和验收要求，轮数不是放过缺陷的理由。
5. **验证当前候选。** 先验证原始失败用例、同类边界及受影响模块，格式与静态检查随小批修改运行；收齐已知修复后固定候选，执行项目要求的完整门禁。使用现有执行入口，绑定实际输入、环境、命令、运行身份、日志与真实退出码。同一输入、环境和命令保留一个有效运行；观察超时先检查原作业，确认结束或不存在后才重开。已有成功证据仅在输入、环境、验证范围及相关外部条件均未变时复用。
6. **完成阶段交付。** 全部阶段验收满足、已确认 P0/P1/P2 清零、必需检查通过后，提交阶段 PR，在已有授权内合入集成分支，验证合并结果并同步涉及的本地分支，再推进后续阶段并清理不再需要的 worktree。
7. **完成总交付。** 全部 spec 完成后，以总交付起始 SHA 为基准调用 `code-review`，覆盖总 diff 与跨 spec 行为；修复与验证沿用步骤 4、5。总审查通过后，创建或更新总 PR 并标为 ready。仅在用户明确要求时继续合并总 PR，验证结果并同步本地分支。

审查调用约定：提供对应的固定基准 SHA、最新已提交候选、规格与标准指针、已有审查报告。同一基准、候选、规格、标准及覆盖范围只执行一份审查，主线程接收报告并处理缺口。复审由 `code-review` 核对修复、新变更及受影响调用路径，结合仍有效的覆盖记录保持从基准到候选的完整覆盖；影响无法界定时扩大检查。阶段报告作为总审查的输入，不能代替跨阶段审查。

在项目既有交付记录中保留一个当前入口：阶段、候选、负责人、未关闭问题、有效作业、证据路径及下一动作。关键结果与运行依赖保存到持久位置；恢复先核对路径、进程身份与结果，原句柄丢失不代表原作业结束。主线程依据新增证据派发、验收、等待或推进；已授权的下一步满足条件就执行。

区分产品失败、执行器故障、环境阻塞与有效等待。执行器故障在现有入口定点修复；有独立工作时继续推进。剩余工作全依赖外部条件时，按平台的 blocked 条件报告缺口与解锁动作。超时、预算到限和证据缺失都不算通过。本 skill 的协调规则属于流程约束；硬预算与执行截止须由实际 Goal 或执行器落实，未启用时明确说明。

全部验收满足、P0/P1/P2 清零、必需检查通过、PR 达到约定状态且本地分支已同步，才结束 goal。报告 PR、验证结果和剩余问题；总 PR 仅 ready 时明确注明待合并。
