# Spec 完整交付

调用：Codex 用 `/goal $spec-delivery`，Claude Code 用 `/ghost-agent-skills:spec-delivery`。复用当前对话已确认的规格、工单和授权；缺少必要信息才提问。

## 选择实施方式

按工作范围选择当前安装的 `mattpocock-skills-zh` skill，只读取当前路径所需的 skill 及其依赖，保持 Matt 文件原样。

| 工作范围 | 执行方式 |
| --- | --- |
| 一个可连续实施并验证的结果 | 调用 `implement` |
| 已有多张已确认工单，或存在真实阶段依赖 | 调用 `implement-spec` |
| 涉及多个独立 Git 仓库 | 必须读取 [多仓交付](references/multi-repo.md)，各仓分别选择上述实施方式 |

多仓和任务规模分别判断。子仓默认直接实施总规格中分配的范围。需要任务图但尚无工单时，先调用 `to-tickets`，沿用它的拆分确认流程。只有存在独立验收结果、真实阶段依赖或明确并行收益才拆票。已批准的拆分直接复用；普通编码步骤保留为检查清单，派生工单引用总规格。

本 skill 负责调用衔接、结果复用和交付条件。实施流程沿用所选 Matt skill；审查时读取 `code-review`，沿用其方法、角色和报告格式。

## 开发与验收

1. **固定交付范围。** 确定规格、责任范围、验收项、项目检查入口，以及每个仓库的起始 SHA 和分支流向。有真实阶段时再定义阶段基准和阶段验收。采用阶段 PR → 集成分支、总 PR → 目标分支时，区分两类 PR 的范围。需要真实服务或实机时，先验证最小真实路径可执行。缺口记录证据、责任人、解锁条件和下一动作；新增要求单独明确归属。
2. **调用所选实施流程。** 传入本仓责任范围、验收项、规格指针和基准 SHA，明确文件归属。使用 `implement-spec` 时，沿用任务图、TDD、实现者与 merger 分工，并遵守项目对分支和 worktree 的约束。同阶段后继等待前置工单验收并进入阶段候选；跨阶段后继等待前置阶段审查通过并集成。同一 checkout 保持一个写入负责人，Git 操作串行。调用前说明：审查使用已提交候选，PR 最终 ready 和 worktree 清理由本 skill 在验收后处理。
3. **承接审查与复盘。** 复用实施流程已有的首审和集中修复结果。按需求或真实阶段调用一次 `retro`，处理本次范围内已确认的 P0/P1/P2；长期环境改进另记后续事项。候选、规格、标准或覆盖范围变化时，按下方约定调用 `code-review` 补审。修复后的复审只在新证据使复盘结论失效时补对应复盘。
4. **集中关闭发现。** 同类发现交给同一个修复实现者。同一类别两轮修复后仍未关闭，先读取 `diagnosing-bugs`，建立能区分原因的定点反馈，补齐有限的输入分类与成对边界，再继续修改。保留未完成状态和验收要求，轮数不是放过缺陷的理由。
5. **验证当前候选。** 先验证原始失败用例、同类边界及受影响模块，格式与静态检查随小批修改运行。收齐已知修复后固定候选，执行项目要求的完整门禁。使用现有入口，绑定实际输入、环境、命令、运行身份、日志与真实退出码。同一输入、环境和命令保留一个有效运行；观察超时先检查原作业，确认结束或不存在后才重开。已有成功证据仅在输入、环境、验证范围及相关外部条件均未变时复用。
6. **按约定交付。** 全部验收满足、已确认 P0/P1/P2 清零、必需检查通过后，推进对应 PR 或工单。存在阶段集成时，在已有授权内合入集成分支，验证合并结果并同步涉及的本地分支，再推进后续阶段。总审查须覆盖每仓起始 SHA 到最终候选的完整变更，以及跨阶段行为；沿用仍有效的覆盖记录补齐缺口。多仓还须通过固定版本组合的整体验收。各仓分别管理 PR，总 issue 汇总交付；需要父仓版本快照时更新 gitlink。最终 PR 标为 ready；仅在用户明确要求时合并，随后验证结果并同步本地分支。验收完成后清理不再需要的 worktree。

审查调用约定：提供本仓固定基准 SHA、最新已提交候选、本仓验收范围、总规格与标准指针，以及已有报告。同一基准、候选、规格、标准及覆盖范围只执行一份审查。复审检查修复、新变更及受影响调用路径，结合有效记录保持完整覆盖；影响无法界定时扩大检查。阶段报告是总审查的输入，仍须补齐跨阶段覆盖。

## 持续执行与用户介入

用户要求 Goal 且平台支持时，建立或沿用主会话的实际 Goal。主会话持续等待实施结果、验收、派发修复并推进交付。其他会话仅在需要长期自主迭代时单独启用 Goal，主会话的 Goal 不会自动传递。硬预算与执行截止由实际 Goal 或执行器落实，未启用时明确说明。

进度复用工单、PR、会话状态和现有交付记录。主会话只补充工作范围与会话的映射，以及恢复所需的候选、未关闭问题、有效作业、证据路径和下一动作。关键结果与运行依赖保存到持久位置；恢复先核对路径、进程身份与结果，原句柄丢失不代表原作业结束。

需要用户决策或操作时，使用当前可用的提问机制，说明问题、建议、影响和等待回答的工作。权限请求使用原生审批机制。等待期间继续不依赖回答的工作；同一问题未变化时不重复提醒。通知送达依赖应用与系统设置。

区分产品失败、执行器故障、环境阻塞与有效等待。执行器故障在现有入口定点修复，有独立工作时继续推进。剩余工作全依赖外部条件时，按平台的 blocked 条件报告缺口与解锁动作。超时、预算到限和证据缺失都不算通过。

全部验收满足、P0/P1/P2 清零、必需检查通过、PR 或工单达到约定状态且本地分支已同步，才结束交付并完成 Goal。报告各仓候选、PR、验证结果和剩余问题；最终 PR 仅 ready 时明确注明待合并。
