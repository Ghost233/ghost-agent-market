# 容器化开发流程

## 适用范围

沿用用户或项目选定的运行时、工具链和执行入口。仅存在 Dockerfile 不表示要求容器化开发；只运行已有程序时，按项目运行指引执行。

宿主机负责编辑、检索、Git 和编排；依赖安装、代码生成、编译、测试及服务运行在容器内完成。面向用户使用中文，用户另有要求时除外。

## 执行顺序

1. 读取项目容器指引、构建定义和检查入口，确认目标平台、所需服务和配置。已有有效环境检查结果可复用；首次运行或环境变化时，先验证最小执行路径及所需域名的解析和连接。
2. 核对工具链和依赖结果的输入指纹、内容摘要及使用核验。匹配时直接复用，缺失或失效时只更新受影响部分。
3. 同步当前源码，在开发容器内定点编译、测试和调试。修复通过后扩大到受影响模块及实际消费方，最终候选执行项目要求的完整测试和必需检查。
4. 按下表决定是否打包。交付产物对应已验证候选；打包后完成项目要求的镜像验收。发布和部署仅在任务已授权时执行。

| 输入变化 | 执行动作 |
|---|---|
| 普通源码、测试代码 | 复用依赖环境，容器内增量编译和定点测试。 |
| 环境变量、运行配置 | 更新配置并重启进程；配置写入镜像时重新打包。 |
| Compose 端口、挂载、运行用户 | 重新创建受影响服务并验证。 |
| 依赖清单、锁文件、本地依赖、实际依赖图或依赖编译参数 | 更新项目依赖层，再编译和验证业务。 |
| 工具链、系统依赖、目标平台或对应构建配方 | 更新受影响基础层及后续层。 |
| Dockerfile、入口脚本、打包方式、最终交付或项目镜像门禁 | 构建实际运行镜像，验证启动、挂载、用户和权限。 |

## 工具链与依赖复用

以 Go 项目为例，三层这样划分。名称仅作示例，其他语言按相同职责分层。

| 层 | Go 示例 | 保存或执行的内容 |
|---|---|---|
| 第一层：工具链基础层 | `go-toolchain` | 固定 Go 版本、基础镜像摘要、目标平台和系统编译工具，不放项目依赖与业务源码。 |
| 第二层：项目依赖层 | 基于 `go-toolchain` 的 `go-base` | 按项目实际依赖图提前下载 SDK 和其他模块、预编译依赖，保存 `GOMODCACHE` 和匹配的 `GOCACHE`。 |
| 第三层：业务编译阶段 | 从 `go-base` 创建开发容器 | 注入当前业务源码，执行 `go build`、`go test`，生成程序和测试结果。改业务代码时在这里重新编译。 |

前两层使用镜像或可持久复用的构建阶段；第三层容器可以复用或重新创建。交付时再将已验证程序和运行依赖组装为最终运行镜像。

- 工具链固定版本或摘要及目标平台。依赖指纹包含父层、清单、锁文件、本地依赖及影响依赖选择和编译的输入；业务源码候选另行记录，普通源码变化不使依赖层失效。
- 准备依赖时核验实际生产和测试依赖图、本地引用及清单一致性。清单或锁文件的必要改动先写回源码，再固定输入。
- 依赖和所需编译缓存须随依赖层交付，新建开发容器能够直接使用。仅留在构建器缓存挂载中的内容不算交付。使用项目现有 Registry、归档或持久构建存储保存，记录获取入口；受授权或环境限制无法保存时，说明复用范围及缺口。
- 依赖标识由构建流程按指纹生成或由现有缓存机制管理，不为内部复用增加运维手填变量。输入未变时，正式编译和测试不重复安装依赖。

### Go

依赖层保存 `GOMODCACHE`，预编译实际需要的依赖并保存 `GOCACHE`；仅执行 `go mod download` 不够。Go 版本、架构、CGO、构建标签及普通测试、race 等模式须与后续编译匹配。

正式构建使用 `-mod=readonly`，已有 vendor 模式沿用 `-mod=vendor`。首次准备或依赖输入变化后，从新容器验证禁用依赖下载时所需目标仍可编译或测试；上述 `-mod` 选项本身不能证明无下载。缺少依赖时返回准备阶段。

### SDK 与多语言依赖

SDK 提前按任务指定版本完成下载、校验、安装及所需编译。SDK 版本和传递依赖纳入指纹，各语言分别判定是否失效。Go 本地 SDK 的 `replace` 或工作区输入参与核验；Node 工具链、清单、锁文件和安装输入未变时复用安装结果，仅改脚本不重复安装。

运行时 SDK 的安装结果须匹配最终平台和系统库。最终镜像直接继承或复制已准备的 SDK 及运行依赖，组装和启动时不再下载或安装。验收核对版本，并在禁止下载 SDK 的条件下验证其可用；缺失或版本不符时返回准备阶段。

## 开发环境与作业

- 临时测试数据、临时数据库文件和中间产物默认放在容器可写层或容器内临时文件系统，测试完成并取回必要结果后随容器销毁。仅在明确需要持久化或交换输入、输出时使用宿主挂载；共享依赖缓存按前述复用规则保留。
- 源码同步包含新增、修改和删除，范围限定为源码工作副本，保留依赖和编译缓存。优先使用语言自身的增量缓存，仅在已有可靠影响分析时跳过整个程序的构建。
- 本机 Apple container 使用 VirtioFS 时，编译工作副本、依赖树和缓存放在容器自己的 Linux 文件系统，用复制或归档注入源码。检查实际挂载类型；宿主绑定挂载用于指定的持久业务数据和小范围输入、输出交换。
- 共享 builder 沿用既定资源、DNS 和互斥入口；需要不同资源时使用独立容器。并行作业按实际数据库、目录及清理范围隔离，共用资源时互斥覆盖执行和清理全过程。
- 失败先保留现场，检查进程、真实退出码和首个原始错误。源码问题在现有依赖环境中修复；环境输入变化才更新对应层。观察超时先确认原作业状态，同一输入、环境和命令只保留一个有效作业。
- 成功证据只在输入、环境、检查范围及相关外部条件未变时复用。重建或重跑完整门禁前说明失效原因；超时、取消、跳过和强制清理不计为通过。

完成时记录源码候选（含未提交构建输入的哈希）、依赖指纹与内容标识、产物标识、验证命令、日志和真实退出码，列明未完成项。先取回并核验结果，再删除本轮临时容器；保留依赖镜像、约定持久数据及仍需运行的服务。
