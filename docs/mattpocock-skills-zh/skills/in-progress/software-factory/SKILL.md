**软件工厂**是一个代理系统，它把工单、PR 和定期安排转成已合并的代码，并部署到用户选择的远程基础设施。本 skill 提供设计软件工厂的词汇。讨论或绘制工厂时，只使用这些术语；用户使用“避免”中的词时，指出规范术语。

## 任务与运行

**任务（Task）**：
工厂执行的一类工作，定义一次，可多次运行，例如审查、探索、实施和渐进收紧。任务可以处理一张工单、一个 PR，也可以处理整个代码库。
_避免_：用 job、workflow 或 action 命名任务。CI 厂商的 workflow 文件和其中的 jobs 是接入任务的位置，不是任务本身。

**触发器（Trigger）**：
开始一次运行的事件，可以来自工单跟踪器或 Git 托管平台的变化、编排器中的时钟，或另一次运行。

**运行（Run）**：
一项任务从触发到结束，在一个运行器上执行一次，作为黑盒处理。一次运行可通过编排器中的逻辑直接触发后续运行，也可通过更改工单跟踪器或 Git 托管平台来触发。运行不会等待人：它会结束，之后由人对工单跟踪器或 Git 托管平台的修改触发新运行。
_避免_：session。

**运行器（Runner）**：
执行一次运行的可丢弃机器。即使机器长期运行，其上的任何内容也不会跨运行保留；一次运行对之前运行的记忆只来自工单跟踪器、Git 托管平台和编排器。
_避免_：server、host、box、compute、sandbox。

## 服务

**工单跟踪器（Ticket tracker）**：
存放工单的地方，也是工厂与人交互的界面：人们通过创建工单安排工作，在评论中与代理交流；对工单的修改会触发运行。
_避免_：issue tracker、ticket manager、project board。

**工单来源（Ticket source）**：
工厂外部向工单跟踪器创建工单的任何来源，例如反馈按钮、监控器、错误跟踪器或收件箱。
_避免_：data source、trigger source、intake。

**Git 托管平台（Git host）**：
存放分支、PR 和审查的地方。
_避免_：code host、forge、repo。

**编排器（Orchestrator）**：
接收触发器、在运行器上启动运行，并记录哪些运行正在排队、执行或已经结束的组件。
_避免_：dispatcher、scheduler、control plane。

**可观测性平台（Observability platform）**：
运行器向其发送日志、追踪和状态，让人看到每次运行内部发生了什么。它是可选项：承担运行器或编排器角色的产品通常已经展示了足够信息。运行不会直接依据平台中的信息决策，必须先由某个来源将信息写入工单跟踪器或 Git 托管平台。
_避免_：observability、logs、monitoring、dashboard。

## 设计工厂

设计包含两部分：**服务**，即由产品填充的各个位置；以及**任务**，其运行推动工作穿过这些服务。

先从用户的问题出发，例如尚未分诊的工单、等待自动审查的 PR、需要迁移到更严格自动检查的代码，或无人阅读的缺陷。用户提出问题或不知道该构建什么时，读取 [EXAMPLE-TASKS.md](EXAMPLE-TASKS.md)，查找解决常见问题的任务。

### 从小规模开始

每个触发器都会加速运行；只有加速没有刹车会产生大量低质量内容。这里有三种刹车：

- **自动检查**：每次运行都必须通过的确定性门禁，例如类型检查、lint 和测试。
- **自动审查**：单独启动一次运行，在没有先入上下文的情况下，对照代码库标准和工单（如果有）阅读 diff。
- **人工审查**：合并前由人阅读 PR；把人工发现转化为新的自动检查和更精确的自动审查。

每次只增加一个自动触发器，开始时限制频率，例如十份缺陷报告处理一份，或每天定时运行一次；每个 PR 都经过人工审查。确认刹车值得信任后再逐步提高频率，每个运行循环在交给人之前都限制为少数几次尝试。

### 填满每个位置

每项服务都是一个位置。同一产品可以填充多个位置，一台服务器也可以承载多个服务。以下是三个并列方案：

| 服务 | 全部使用 GitHub | 使用 Linear 工单 | 自建跟踪器 |
| --- | --- | --- | --- |
| 工单跟踪器 | GitHub Issues | Linear | 自建应用 |
| 工单来源 | 反馈按钮 | 反馈按钮、监控器 | 反馈按钮、监控器 |
| Git 托管平台 | GitHub | GitHub | GitHub |
| 编排器 | GitHub Actions | 自有服务器及数据库 | 自建应用 |
| 运行器 | Actions runner | Actions、E2B、Daytona 或 VPS | 自建应用或沙箱 |
| 可观测性平台 | 无，Actions 运行页面已足够 | LLM 追踪平台 | 自建应用 |

用户为某个位置选择产品时，先读对应调查以了解类别和决策问题，再自行调研当前选项：

- [TICKET-TRACKERS.md](TICKET-TRACKERS.md)
- [GIT-HOSTS.md](GIT-HOSTS.md)
- [RUNNERS.md](RUNNERS.md)
- [OBSERVABILITY-PLATFORMS.md](OBSERVABILITY-PLATFORMS.md)

购买服务，自建任务：任务承载用户的设计，服务是通用的。优先选现成的工单跟踪器，因为它可靠、大家熟悉，也容易让外部用户参与。

### 逐项审视任务

对每项任务回答：

1. 什么会触发它？
2. 它做什么，读写哪些服务？
3. 它接下来触发什么？
4. 人在哪里重新介入？
5. 如何防止两次运行重复做同一工作？

对每个工单来源回答：如何防止它重复创建同一工单？

每个服务位置都已选定产品（可观测性平台也可以明确选择不用），而每项任务及每个工单来源都已回答对应的全部问题时，设计才算完成。
