## 它做什么

`to-questionnaire` 把你无法独自确定的决策整理为**问卷**：一份 Markdown 文档，交给掌握缺失信息的那个人。对方可以异步填写，也可以与你开会时一起回答。

它追问**发送安排**，不追问主题。不了解主题正是你向别人提问的原因，围绕主题访谈没有意义。所以它只问你总能回答的两件事：发给谁，希望对方提供什么，再让文档中的每个问题针对两者之间的**缺口**。

## 何时使用

输入 `/to-questionnaire` 调用，[代理](https://www.aihero.dev/ai-coding-dictionary/agent)不会自行使用。

决策受阻，因为所需知识掌握在另一个人手里时使用：客户、领域专家、掌握业务规则的负责人，或另一团队的同事。选择哪个 skill，取决于答案在哪里：

| 答案所在位置 | 使用 |
| --- | --- |
| 自己的头脑中，但尚未梳理清楚 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的头脑中 | `to-questionnaire` |
| 还没有人知道，需要先看到可供回应的东西 | [prototype](https://aihero.dev/skills-prototype) |

常见情形是[深入追问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话停滞，因为部分问题不是你能回答的。在同一段对话中运行 `/to-questionnaire`，把这些问题交出去，再带回答案继续。

## 发送安排

访谈只有两次交流，之后停止。

- **发给谁？** 对方的角色、专业能力，以及与你的关系。这决定语气和文档需要包含多少背景。外部客户需要交代背景，队友无需同样的说明。
- **需要对方提供什么？** 你无法独自确定的具体决策或事实。这成为成稿的检查清单，你列出的每项内容都会对应一个问题。

随后全部是起草工作。Skill 把文件写到当前目录中的 `to-questionnaire-<slug>.md`。无需初始化工作区，也无需配置。

## 文档形式

文档是**信息发现问卷**：你缺少背景，而收件人掌握背景。这决定了它的形式：

- 用一句目的说明指出哪个决策依赖问卷，附简短背景，让完全不了解前情的收件人也能理解。
- 问题按**最重要的在前**排列，并按主题分组；异步交流可能只有一次回复机会。
- 每个问题只包含一个意思，下面留回答占位。只有可能被误解的问题，才附“为什么重要”说明。
- 明确允许回答“我不知道”，因为标记出的不确定性有用，而像事实一样自信的猜测没有用。
- 最后留一个兜底问题：有没有我们没问到、但应该知道的内容？

文档有意排除两种能力。它不带**分支**：问题是分组的平铺列表，不会根据 A 的答案跳过 D。它也不面向**多个收件人**：每次运行只为一个人生成一份文档。

## 常见问题

**它会读取追问会话，从中提取问题吗？**
没有单独的这一步。Skill 不设置输入提取阶段，而是先问发送安排，再起草。它能在追问会话后使用，是因为在**同一段对话**中运行，[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经位于[上下文](https://www.aihero.dev/ai-coding-dictionary/context)里，起草时可以参考。如果新开会话，它不了解之前的追问，需要你在回答“需要对方提供什么”时重新说明主题。

**答案掌握在不同人手里，可以按收件人拆分吗？**
不能。第一步询问单数的收件人，整份文档的语气和背景都针对这个人。三个人各掌握一部分答案时，运行三次，每人一次。有人要求一份按专业或角色分派问题的文档，但这个能力没有发布。

**问题有依赖关系吗？会按之前的答案跳过章节吗？**
不会。有依赖的问题设计曾被探索，但没有发布。输出是静态文档：按主题分组，最重要的在前，所有问题都需回答。对分支设计的质疑有道理：[模型](https://www.aihero.dev/ai-coding-dictionary/model)在实际收到答案前，提前规划超过两三个问题就容易规划失误，而分支文档需要在收到任何答案前规划所有问题。

**收件人也不知道怎么办？**
文档要求对方直接说明，明确接受“我不知道”和部分答案。标记出的不确定性比猜测有价值，因为模糊答案与自信的错误答案进入上下文后，看起来并无区别。

**它会发送到 Slack、问题跟踪器或邮件吗？**
不会。它只在当前目录写 Markdown 文件，并告诉你路径。发送由你完成：粘贴进[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)、放进 Slack 对话、作为邮件附件，或在共享屏幕上打开并现场回答。这四种方式都有人手动使用。

**这只是批量版 `/grill-me` 吗？**
不是。`grill-me` 已经按**轮次**提问：一次询问当前整个前沿，再根据回答重新计算，已经满足“一次给我所有问题”的需求。`to-questionnaire` 的区别是答案掌握在谁手里。想更快地自己回答，用 `grill-me`；想从另一个人那里获取答案，用这个。

**不用 skill，直接要求代理做这件事可以吗？**
可以。在 skill 出现前，很多人已经这样做：`OPEN_QUESTIONS.md` 文件、发送给客户的表格，或为每个未回答问题创建“需要更多信息”工单。Skill 提供两点价值：访谈不偏移到主题本身，文档形式适合非技术收件人填写。已有有效内部格式时，无需使用它。

## 有效运行的表现

- 它问收件人和所需回复，然后停止提问。开始问主题本身，就偏离了 skill。
- 你列出的“需要对方提供什么”每一项，都能对应到文件中的问题。
- 问题针对*收件人*知道的内容，而非原样复制你自己的待解问题。
- 把文件交给未参与对话的人，对方也知道为什么收到，以及何时回复。
- 收到的答案可以用于新一轮追问，而非又产生一组需要重新问的问题。

## 在流程中的位置

`to-questionnaire` 是随时可用的独立工具。自己的知识不足，下一步需要问另一个人时使用。多数情况发生在流程中途：规划因不该由你决定的内容而停滞。

相邻工具是 [grill-me](https://aihero.dev/skills-grill-me)，区别在于答案在哪里。深入追问从你这里获取答案，问卷从别人那里获取。把回复放进新一轮追问；工作将进入构建时，也可交给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。不确定哪个 skill 适合当前情形时，[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你选择。
