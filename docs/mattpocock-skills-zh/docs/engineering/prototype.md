## 它的作用

`prototype` 编写**回答一个问题的一次性代码**：状态模型感觉是否对，或页面应长什么样。先有问题，问题决定构建内容。回答错问题的原型，无论多好看都是浪费。

一次性约束的是代码*写法*，不承诺销毁。不写测试、不加运行所需之外的错误处理、不抽象、不持久化，因为都无助于学习那一件事。两样会保留：答案进入真实代码，原型留在 main 之外的分支，作为答案证据。

## 何时使用

输入 `/prototype`，或任务适合时[代理](https://www.aihero.dev/ai-coding-dictionary/agent)自动使用。

遇到仅谈话无法确定的问题时使用：无法在脑中容纳边缘情况的状态机，或必须并排看三个版本才能想象的页面。此类[追问](https://www.aihero.dev/ai-coding-dictionary/grilling)会话会变长：代理改写、你猜测、范围膨胀。停止追问、构建一次性版本、观察、一句话回答。若现有东西行为错误、想查原因，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；原型探索构建什么，不查已建东西为何坏。

你也可能未经主动选择来到这里：[wayfinder](https://aihero.dev/skills-wayfinder) 在地图上建立 `prototype` 决策[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，由本 skill 处理。

## 两条分支

问题决定分支，产物不同：

- **“这个逻辑／状态模型是否合适？”**：**单个可分享 HTML 文件**。自包含、无构建、无服务器，双击打开。带每次点击重绘的标记状态面板、可任意顺序试模型的自由操作按钮，以及标签式**引导演练**（每标签一场景，下方列按序点击的按钮）。全部用领域语言，可交设计师、PM、领域专家自己试。页面底层是小纯逻辑模块（reducer、machine、一组函数），不含 DOM 代码，验证后能直接移入真实代码。
- **“应该长什么样？”**：同一路由多个**截然不同** UI，通过底部浮动栏与 `?variant=` 参数切换。必须在结构上不同，而非颜色；微调的三个卡片网格回答不了问题。尽可能在真实页面、真实数据和密度下渲染，因为空页上的版本总显得不错。

两者都在内存保留状态，无设置即可启动，每步后显示完整状态。一旦开始加固（加测试、接真实数据库、为未来情况泛化），就不再是原型。

## 原型是一手来源

完成后留下两样，去处不同。

把**答案**（结论及其回答的问题）记在永久位置：提交消息、ADR、实施 issue。Main 中真实代码保留答案。

**原型**是得出答案的可运行证据，不删除，也不进 main，因为无人维护、很快过期。提交到 main 之外一次性 `prototype/<name>` 分支，永不合并，实施 issue 留下指向分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。Main 干净，后来接手的人能找到并重跑。

## 常见问题

**原型不是应删除吗？**
现在不是。过去是构建、留答案、扔代码。最强反对不是速度，而是下个[会话](https://www.aihero.dev/ai-coding-dictionary/session)谁接手、依据什么？文字摘要丢掉说服人的证据。所以现在视为[一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)，落到 main 外 `prototype/<name>`，实施 issue 指向它。改变的是代码位置，而非约束；仍永不合入 main。

**过去构建终端应用，现在呢？**
逻辑分支改生成可分享的单 HTML。终端应用只供已 clone 仓库、安装运行时的人操作，排除了最需要意见的设计师、PM、理解状态意义的领域专家。双击可开、邮件发送后仍可用的自包含文件人人能操作。底层纯逻辑模块没变，仍是移到真实代码的部分。

**该实施时代理却让我 `/prototype`。**
这是已知命名问题。不懂流程的代理把通用又有吸引力的 `prototype` 看作已有工单后的“显然下一步”，即使对话已确定设计也推荐。知道构建什么就逐张 `/implement`。仅在具体设计问题未解、谈话也不能解时做原型。

**应先做整个应用原型再做生产功能，例如给客户演示吗？**
那是恰好同名的另一工件。这里仅限一个问题，“整个应用是什么”不算一个。全应用没有自然停止点，会漂移为生产应用，清理永不发生，无测试、无错误处理的代码最后面对用户。销售演示应明确作为演示构建，明确都非生产。设计问题则缩到该问题。

**怎样在独立会话运行？**
原型有独立目录，会产生大量原提问对话不需要的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)。另处运行，只带回答回来。用 [handoff](https://aihero.dev/skills-handoff) 转移任务并带回答回来。

**这是最快烧 tokens 的方法吗？**
可能，如果对谈话就能回答的问题做原型，或扩展到整功能。重要比较不是 tokens 与零，而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 与构建错误状态模型、到有生产调用者才发现的成本。问题窄、运行短，花费就相称。

## 正常工作的表现

- 能一句话说出原型的问题，写在演示顶部，而不只脑中。
- 不读代码的人也能开文件、按演练标签按钮、用自己的话描述逻辑。
- 有人说“这不该可能”或“我以为 X”。这是*想法*缺陷，正是原型目的。
- UI 在布局与信息层级上不同，不只色彩文案；反馈是“B 的页头配 C 的侧栏”。
- 一次坐下就答完。一天后仍构建，问题太大，应拆分。
- 结束后 main 含决策、不含原型，实施 issue 指向仍保留原型的分支。

## 它在流程中的位置

`prototype` 是**随时可用的独立工具**，解决一个设计问题后返回工作。另一个 skill 也会运行它。

最多调用者是 [wayfinder](https://aihero.dev/skills-wayfinder)。地图由**决策工单**构成，`prototype` 是四类型之一，用于“应长什么样”“应怎样行为”这些讨论无法解决的阻塞问题。讨论模糊时 wayfinder 做具体对象供回应，由这里构建。答案解决原型工单，地图将原型作为资产链接。

其他邻居在上下游。[grill-me](https://aihero.dev/skills-grill-me)、[grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可追问问题，不可追问的来到这里，一句答案返回采访。下游验证的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的确定输入，它可内联原型产生的决策密集片段，而非文字转述。其他情况由 [ask-matt](https://aihero.dev/skills-ask-matt) 路由。
