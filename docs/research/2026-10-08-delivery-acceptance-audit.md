## 建议的 Matt 交付流程

### 1. 在第一条真实纵向路径上验证验收环境

spec / tickets 阶段就登记要求 ID、公共测试接缝、关键不变量、验收命令、真实身份与资源、证据类型、预计运行量级。优先实现一条穿过真实接口、执行器或原生启动链的最小路径，提前暴露身份、隔离、GUI 会话、端点与工具链问题。

不要把所有实机和真实服务验证推到功能全部写完之后；这不是要求先做全量 E2E，而是先确认最终验证路径可以执行。

### 2. 用快速循环完成实施和整类修复

实施仍走 TDD。格式、静态分析和定点测试尽早运行。同类缺陷先列必须成立与必须不成立的成对边界，再逐个纵向切片落地。代表性维度有限且追溯原规格；不创建无限“全覆盖”任务。

同一缺陷类别使用固定 ID 和负责人。两轮修复后仍出现同类失败，先停止局部补丁，提交：已排除原因、尚可成立的原因、下一项可区分它们的实验。第三轮不得是又一次无诊断增量的完整重跑。

### 3. 固定候选，集中双轴审查

在局部与受影响模块通过后，由 Standards 与 Spec 两名独立审查者一次汇总已知发现。每个阻断项都要对应原规格或硬标准、失败行为/反例和影响；同类问题集中给同一实现者。普通设计建议单列。

保持从原始基准到最终候选的完整覆盖。复审携带旧覆盖记录，重查新增 diff、修复与受影响的共享调用路径；未变化且不受影响的部分复用证据。若公共边界变化或影响范围不能可靠界定，应扩大审查，不能机械只看改动行。

内层 `implement-spec` 的收尾审查与阶段审查共享一次结果，避免因为调用了两个 skill 而重复执行。总审查负责跨阶段集成行为和最终覆盖核对。

### 4. 把复盘发现分类，再冻结最终完整门禁

复盘仍执行。以下内容保留为本次阻断项：原规格未满足、可信验收所必需的执行器缺陷、当前已发生的 P0/P1/P2 产品问题。环境便利性、一般重构和后续自动化建议登记为独立待办，不自动进入本次候选。

需要在本次修复的内容必须在最终完整门禁前收敛。候选冻结后允许因新发现的真实缺陷重开，但记录具体失效范围；不能为了少跑测试隐瞒缺陷。新增需求走范围变更，不暗中扩大原验收合同。

### 5. 最终门禁、集成、交付证据绑定

保留仓库规定的全部必需检查。为同一候选只维护一个有效完整门禁运行。通过后进入 PR、授权内集成与本地分支同步；合并产生实际产品输入变化时更新相应验证，不能把旧结果直接说成新候选通过。

只有输入、环境、命令、范围与相关外部条件一致且证据完整，才允许复用。README 变化是否能复用取决于它是否属于该检查输入，而非单看文件扩展名。任何未跟踪但参与构建的文件、执行器、配置、锁文件与夹具都应纳入输入登记。

## 最小执行保障

不新增控制平台。优先为已有运行入口补以下能力：

1. `prepare`：记录并复用已验证工具链和依赖；按真正变化的输入重建。多个实现者不能并发覆盖同一工作目录或复制目标。
2. `run`：启动前查询同一运行键是否已有有效作业；区分 setup、测试与 cleanup 时间；保存首个原始错误、真实退出码和业务断言结果。
3. `status`：从持久索引接管运行；核对 PID 加启动时间或容器/远端作业 ID，而非仅保存子线程独有句柄。找不到句柄先查进程和结果文件。
4. `verify`：统一校验输入与产物、环境和证据完整性；返回通过、产品失败、工具失败、环境阻塞、超时或结果未知。cleanup 单独记录，不覆盖原始失败。

这四项是职责划分，不要求制造四个新脚本或 CLI 命令；可直接扩展项目现有入口。

计时必须由工具/运行器持有。模型检查点仅决定是否继续派发；不能保证已经卡住的调用按时返回。对不可可靠取消的工具调用应隔离拥有者，主控不再进入同一阻塞链；保留现场并明确哪些验证仍缺证据。

Goal 预算与运行器墙钟限制分别管理。预算未真正设置或团队计数未验证时，状态必须直说“未启用”或“覆盖范围未验证”。不得换代理、重建 Goal 或重开作业规避原限制。

持久目录中的当前索引保持简短：阶段、候选、未关闭要求、负责人、有效运行 ID、证据指针、已授权下一动作。历史日志另存。不因重写状态、重复读取、重复报告绿测而更新有效进度时间。

## 怎么验证改进有用

先在一个项目的下一次收尾试行，记录从候选就绪到交付的墙钟时间、setup/真实执行/排队/工具等待/返工占用、每个候选的完整门禁次数、同类缺陷重开次数与最迟发现阶段。

目标是减少准备和重开，而非要求任何复杂项目必须在固定分钟内完成。若测试本身只有几十秒，优先减少循环；若每轮十几分钟，先提高前置检查与集中修复质量；若外部调用挂起，优先修执行器的超时与隔离。不要先给五个项目统一叠加更多提示词。
