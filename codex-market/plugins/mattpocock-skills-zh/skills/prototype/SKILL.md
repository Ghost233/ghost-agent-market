# 原型

原型是**用于回答一个问题的一次性代码**。问题决定原型的形态。

## 选择分支

根据用户提示、周边代码，或在用户在线时直接询问，确定要回答哪类问题：

- **“这套逻辑/状态模型是否合理？”** → [LOGIC.md](LOGIC.md)。构建一个可分享的单文件 HTML：包含自由操作按钮和标签页式引导流程，让非开发者也能驱动状态机经历纸面上难以推理的情形。
- **“它应该长什么样？”** → [UI.md](UI.md)。在同一路由生成多个显著不同的 UI 方案，通过 URL 查询参数和悬浮底栏切换。

两个分支产物完全不同，选错会浪费整个原型。如果问题确实含糊且联系不上用户，选择更符合周边代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部写明假设。

## 两个分支的共同规则

1. **从第一天起就按一次性代码处理，并明确标注。** 把原型放在未来实际使用位置附近（对应模块或页面旁），让上下文清楚；同时用名称明确表明它是原型，不是生产代码。一次性 UI 路由必须遵循项目现有路由约定，不新造顶层结构。
2. **运行极其简单。** UI 原型只需项目任务运行器中的一条命令，例如 `pnpm <name>`、`python <path>`、`bun <path>`。逻辑演示则是用户双击即可打开的单个 HTML。启动不应需要思考。
3. **默认不持久化。** 状态保存在内存中。持久化应是原型_验证的对象_，而不是依赖。如果问题明确涉及数据库，使用临时数据库或名称清楚标注“PROTOTYPE — wipe me”的本地文件。
4. **跳过润色。** 不写测试，不添加超出“确保可运行”所需的错误处理，也不做抽象。目标是快速学到东西。
5. **展示状态。** 每次操作（逻辑）或切换方案（UI）后，打印或渲染全部相关状态，让用户看见变化。
6. **完成后留存。** 将验证过的决策融入真实代码，再把原型作为**一手来源**保存：提交到 main 之外的一次性分支，并在实现 issue 中留下指向该分支的上下文指针。同时在 issue 或 commit 中记录答案，即结论以及它解决的问题。main 分支只保留已验证的决策。
