> **Codex 平台说明：** 本版本使用 `$skill-name` 引用或调用其他 skill；Claude Code 版本使用 `/skill-name`。

从用户提供的固定点到 `HEAD`，对 diff 执行双轴审查：

- **Standards**：代码是否符合仓库记录的编码标准？
- **Spec**：代码是否忠实实现来源 issue/规格？

两个轴由**并行子代理**执行，避免上下文互相污染，再由本 skill 汇总发现。

你应该已经获得 issue 跟踪器配置；缺少 `docs/agents/issue-tracker.md` 时运行 `$setup-matt-pocock-skills`。

## 流程

### 1. 锁定固定点

用户指定的内容就是固定点，例如 commit SHA、分支名、tag、`main`、`HEAD~5`。未指定时询问。

只确定一次 diff 命令：`git diff <fixed-point>...HEAD`。使用三点语法，使比较基于 merge-base。同时用 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

继续前确认固定点可解析（`git rev-parse <fixed-point>`）且 diff 非空。错误 ref 或空 diff 必须在此失败，不要留给两个子代理。

### 2. 确定规格来源

按以下顺序寻找来源规格：

1. commit 消息中的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），按 `docs/agents/issue-tracker.md` 中的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 仍未找到时询问用户。用户确认不存在规格时跳过 **Spec** 子代理，并报告“没有可用规格”。

### 3. 确定标准来源

查找仓库中说明代码编写方式的所有内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除仓库文档外，Standards 轴始终包含下方**坏味道基线**：Fowler《重构》第 3 章的一组固定代码坏味道，即使仓库没有记录标准也适用。遵守两条规则：

- **仓库标准优先。** 已记录的仓库标准始终获胜；若仓库明确认可基线会标记的做法，就不报告该坏味道。
- **始终是判断项。** 每个坏味道都是带标签的启发式判断（如“可能存在 Feature Envy”），绝不是硬性违规；同时跳过工具已经强制执行的事项。

每项按“*是什么* → *如何修复*”描述，并与 diff 对照：

- **Mysterious Name（神秘命名）**：函数、变量或类型名称没有揭示其作用或内容。→ 重命名；若找不到诚实名称，说明设计含糊。
- **Duplicated Code（重复代码）**：同一逻辑形状出现在多个变更块或文件。→ 抽取共享形状并由两处调用。
- **Feature Envy（依恋情结）**：方法访问其他对象数据多于自身数据。→ 把方法移到它依恋的数据上。
- **Data Clumps（数据泥团）**：相同字段或参数总是一起传递，暗示一个类型应当诞生。→ 封装成类型后传递。
- **Primitive Obsession（基本类型偏执）**：用基本类型或字符串代表值得拥有独立类型的领域概念。→ 为概念创建小型类型。
- **Repeated Switches（重复 switch）**：针对同一类型的 `switch`/`if` 级联在变更中反复出现。→ 使用多态，或让两处共享同一映射。
- **Shotgun Surgery（霰弹式修改）**：一个逻辑变更迫使多个文件分散修改。→ 把共同变化的内容集中到一个模块。
- **Divergent Change（发散式变化）**：同一文件或模块因多个无关原因被修改。→ 拆分，使每个模块只因一个原因变化。
- **Speculative Generality（夸夸其谈的通用性）**：为规格没有的需求添加抽象、参数或 hook。→ 删除并内联，直到真实需求出现。
- **Message Chains（消息链）**：调用者依赖不应知道的长 `a.b().c().d()` 导航。→ 在第一个对象的方法后隐藏导航。
- **Middle Man（中间人）**：类或函数主要只是继续委托。→ 删除中间层，直接调用真实目标。
- **Refused Bequest（拒绝遗赠）**：子类或实现者忽略或覆盖大部分继承内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

**Standards 子代理提示**包含：

- 完整 diff 命令和 commit 列表。
- 步骤 3 找到的标准来源文件，以及**步骤 3 的完整坏味道基线**；子代理无法从其他地方获得。
- 简报：“按文件/变更块报告：(a) diff 中每处违反已记录标准的位置，并引用标准（文件 + 规则）；(b) 发现的基线坏味道，注明名称并引用变更块。区分硬性违规与判断项：文档标准违规可以是硬性问题，基线坏味道始终是判断项，仓库标准覆盖基线。跳过工具已强制执行的内容。限 400 词。”

**Spec 子代理提示**包含：

- diff 命令和 commit 列表。
- 规格路径或已获取的内容。
- 简报：“报告：(a) 规格要求但缺失或只部分实现的内容；(b) diff 中未被要求的行为（范围蔓延）；(c) 看似已实现但实现方式错误的要求。每项发现引用规格原文。限 400 词。”

规格缺失时跳过 Spec 子代理，并在最终报告中注明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下原样或轻度整理两个报告。**不要**合并或重新排序发现；两个轴刻意保持独立（见“为什么使用两个轴”）。

最后用一行总结每个轴的发现总数，以及_各轴内部_最严重的问题（如有）。不要跨轴选出单一最严重项，否则会破坏分离目的。

## 为什么使用两个轴

变更可能通过一个轴，却在另一个轴失败：

- 代码遵循所有标准，却实现了错误需求 → **Standards 通过，Spec 失败。**
- 代码准确实现 issue 要求，却破坏项目约定 → **Spec 通过，Standards 失败。**

分别报告可防止一个轴掩盖另一个轴。
