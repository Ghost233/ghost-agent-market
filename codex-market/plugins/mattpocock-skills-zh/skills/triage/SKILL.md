# 分诊

通过一组小型分诊角色状态机推进项目 issue tracker 上的 issue。

若 tracker 配置将外部 pull request 也视为请求入口，分诊同样覆盖它们：**PR 就是附带代码的 issue**。它使用相同角色、状态和状态机，差异会在下文以“对于 PR”标注。裸 `#42` 应根据 tracker 配置解析为 issue 或 PR。

分诊期间发布到 issue tracker 的每条评论或 issue 都必须以此免责声明开头：

```markdown
> *此内容由 AI 在分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写经得起时间变化的代理简报。
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库规则。

## 角色

两个**类别**角色：

- `bug`：已有内容损坏。
- `enhancement`：新功能或改进。

五个**状态**角色：

- `needs-triage`：等待维护者评估。
- `needs-info`：等待报告者补充信息。
- `ready-for-agent`：规格完整，可交给 AFK 代理。
- `ready-for-human`：需要人类实现。
- `wontfix`：不会处理。

对于 PR，状态针对附带的代码解释：`ready-for-agent` 表示已附代理简报，代理应继续处理 diff；`ready-for-human` 表示可由人合并。

每个已分诊项必须恰好有一个类别角色和一个状态角色。状态冲突时先标记并询问维护者，不要继续操作。

以上是规范角色名，tracker 上的实际标签可能不同。应已提供映射；没有则运行 `$setup-matt-pocock-skills`。

通常，无标签项先进入 `needs-triage`，再转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；遇到异常转换应先指出并询问。

## 调用

维护者以自然语言调用 `$triage`，例如：

- “显示所有需要我注意的内容。”
- “看看 #42。”
- “把 #42 移到 ready-for-agent。”
- “有哪些内容可供代理领取？”

## 显示需要注意的内容

查询 tracker 并按最旧优先展示三个分组：

1. **无标签**：从未分诊。
2. **`needs-triage`**：正在评估。
3. **报告者在上次分诊记录之后有新活动的 `needs-info`**：需要重新评估。

若 PR 在范围内，把外部 PR 放进同一分组，并在每行标记 `[PR]` 或 `[issue]`。发现阶段只显示 tracker 配置定义的**外部** PR；协作者正在进行的 PR 不属于分诊工作。但用户明确点名的 PR 无论作者是谁都应分诊。

展示每组数量和每项的一行摘要，让维护者选择。

## 分诊指定 issue 或 PR

1. **收集上下文。** 阅读完整正文、评论、标签、作者和日期；PR 还要阅读 diff。解析旧分诊记录，避免重复提问。按项目领域词汇探索代码库，并遵守相关 ADR。对代码库执行两项检查：(a) **冗余检查**——按领域概念而非请求原话，搜索是否已有目标行为的实现，并报告搜索位置；若存在，按“已实现”的 `wontfix` 进入步骤 5。(b) **既往拒绝检查**——阅读 `.out-of-scope/*.md`，指出与本请求相似的记录。
2. **提出建议。** 向维护者说明推荐的类别、状态和理由，并概括相关代码库现状，包括是否已经实现。等待指示。
3. **验证主张。** 深入追问前先验证请求是否成立。bug 按报告步骤复现；PR 则检出 diff 并运行相关测试或命令，确认它确实做到所声称的内容。报告结论：已确认（附代码路径）、失败，或信息不足。确认过的结果能产生更强的代理简报。
4. **需要时深入追问。** 同时运行 `$grilling` 与 `$domain-modeling`，每轮提出一组问题，逐步明确请求；决定落地时同步更新 `CONTEXT.md` 和 ADR。
5. **应用结果。**
   - `ready-for-agent`：发布代理简报评论，格式见 [AGENT-BRIEF.md](AGENT-BRIEF.md)。
   - `ready-for-human`：使用相同结构，并说明无法委派的原因，例如判断工作、外部访问、设计决定或人工测试。
   - `needs-info`：使用下方模板发布分诊记录。
   - `wontfix`：根据原因评论并关闭：
     - **已实现**：指出实现位置；不要写入 `.out-of-scope/`，因为该知识库只记录被拒绝的请求。
     - **拒绝 bug**：礼貌解释后关闭。
     - **拒绝 enhancement**：写入 `.out-of-scope/`，在评论中链接，再关闭；见 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)。
   - `needs-triage`：应用角色；已有部分进展时可选写评论。

## 快速覆盖状态

维护者说“把 #42 移到 ready-for-agent”时，应信任并直接应用。先确认即将执行的角色变更、评论和关闭操作，然后执行，不进行深入追问。若没有追问会话却要移到 `ready-for-agent`，询问是否需要编写代理简报。

## needs-info 模板

```markdown
## 分诊记录

**目前已经确认：**

- 要点 1
- 要点 2

**仍需你补充（@reporter）：**

- 具体问题 1
- 具体问题 2
```

把深入追问中已经解决的内容全部写入“目前已经确认”，避免丢失。问题必须具体且可执行，不能只写“请提供更多信息”。

## 恢复旧会话

若 issue 或 PR 已有分诊记录，先阅读并检查报告者是否回答了待解决问题，再展示最新情况。不要重复询问已经解决的问题。
