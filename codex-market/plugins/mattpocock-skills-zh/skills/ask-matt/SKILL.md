# 询问 Matt

无需记住每个 skill，直接询问。

**工作流**是一条穿过多个 skills 的路径。大多数任务沿一条**主流程**前进，另有若干**入口匝道**汇入。其余 skill 要么独立运行，要么作为底层词汇层。

## 主流程：想法 → 交付

大多数工作都走这条路：有一个想法，并希望把它实现。

1. **`$grill-with-docs`**：通过访谈打磨想法。只要**正在工作目录中处理任务**，就从这里开始；它有状态，会把学到的内容保存到 `CONTEXT.md` 和 ADR。没有工作目录时使用 `$grill-me`（见“独立使用”）。两者都运行 `$grilling` 原语，但仓库存在时，能留下书面记录的 `$grill-with-docs` 更合适。
2. **分支——每个问题都能在对话中确定吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看到的 UI），绕道原型，并用 **`$handoff`** 双向衔接（原型位于独立目录，正是 handoff 的适用情形；见“阶段边界”）：
   - 先运行 **`$handoff`**，再基于交接文件打开新会话；
   - 使用 **`$prototype`** 以一次性代码回答问题；
   - 再运行 **`$handoff`** 带回所学，并从原始想法会话引用它。
3. **分支——这是跨多会话的构建吗？**
   - **是** → 运行 **`$to-spec`** 将会话整理成规格，再用 **`$to-tickets`** 拆成曳光弹式工单，每张工单声明其**阻塞边**。本地跟踪器在 `.scratch/<feature>/issues/` 下每张工单一个文件，人工按阻塞优先处理；真实跟踪器使用原生阻塞链接。对每张已解除阻塞的工单单独运行 **`$implement`**，并在工单之间 **`/clear` 上下文**。每张工单都应自包含。
   - **否** → 在当前上下文直接运行 **`$implement`**。

   两种情况下，**`$implement`** 都会在内部驱动 **`$tdd`**，每次完成一个红绿切片，再在提交前运行 **`$code-review`**，从 Standards 与 Spec 两个轴审查 diff。无需完整规格、只想测试优先构建具体行为时可单独用 **`$tdd`**；需要从固定点审查分支或 PR 时单独用 **`$code-review`**。

### 上下文卫生

步骤 1–3 保持在**同一个不中断的上下文窗口**中；在 `$to-tickets` 完成前不要 compact 或 clear，使追问、规格和工单建立在同一思路上。随后每个 `$implement` 从工单开始使用全新上下文。

限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**，即模型仍能敏锐推理的窗口范围（先进模型约 150k token）。如果会话在 `$to-tickets` 前接近上限，不要带着退化上下文硬撑；在最近的阶段边界执行 `/compact` 后继续。

## 入口匝道

以下起始情形会产生工作，随后汇入主流程。

- **缺陷和请求堆积** → **`$triage`**。让 issue 依次经过分类角色，产出代理可直接处理的 issue，随后由 **`$implement`** 接手。

  分类只用于**不是你创建的**原始 issue，例如缺陷报告和传入的功能请求。`$to-tickets` 生成的工单已经适合代理处理，**不要再次分类**。

- **某处损坏** → **`$diagnosing-bugs`**。用于难以一眼看清的缺陷、间歇性 flaky failure，以及两个已知良好状态之间潜入的回归。建立能在*该缺陷*上变红的一条命令所构成的**紧密反馈循环**前，不做理论推断；随后用回归测试修复。如果最终发现缺少能锁定缺陷的良好接缝，事后分析交给 **`$improve-codebase-architecture`**。

- **巨大而模糊、单次会话容纳不下的绿地项目或大型功能** → **`$wayfinder`**，这是认知要求最高的流程。当抵达目的地的道路尚不可见时，它会在 issue 跟踪器绘制由**决策工单**组成的**共享地图**，逐一解决，产出**决策而非交付物**，直到迷雾消退、道路清晰。`$grill-with-docs` 用于单次会话能掌握的想法；wayfinder 更慢、更密集，只用于无法在一次会话掌握的工作，不用于范围清晰的功能。

  地图清晰后，**只交接，不构建**：在 **`$to-spec`** 处汇入主流程，把地图中相互链接的决策压缩为可构建计划，再照常运行 `$to-tickets` 和 `$implement`。直接从地图进入 `$implement` 会跳过压缩并丢失链接细节；只有工作最终确实很小时才可直接实现。

## 代码库健康

这里不是功能开发，而是维护。

- **`$improve-codebase-architecture`**：有空时运行，让代码库持续适合代理操作。它发现**深化机会**；选择一个就会_产生想法_，可在 `$grill-with-docs` 处进入主流程。该 skill 负责调查候选项，**`$codebase-design`** 则负责设计选中的方案。

## 底层词汇

两个模型调用型参考位于其他 skills *下方*，分别是各自词汇的单一事实来源。问题出在**用词**而非流程时直接查阅，也可让上层 skills 自动调用。

- **`$domain-modeling`**：强化项目的_领域_语言，质疑模糊术语，拆解过载词（例如“账户”承担三种含义），把难以逆转的决策记录为 ADR。`$grill-with-docs` 通过它保持 `CONTEXT.md` 是整洁术语表。
- **`$codebase-design`**：用于设计模块_形状_的深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），即在干净接缝的小接口后隐藏大量行为。`$tdd` 和 `$improve-codebase-architecture` 都使用这些术语。

## 阶段边界

**阶段**是会话中的一块工作，例如追问、实现、QA。在两个阶段的**边界**有五种选择，这是整张地图中最模糊的决策：

- **Continue**：留在当前会话，无成本、无损失。
- **`/clear`**：当前内容与下一阶段无关时清空窗口。
- **`$handoff`**：编写可移植 Markdown，只用于**新执行环境**、**新目录**、**同事**，或在**阶段中途**分叉旁支任务；它提供可移植性。
- **Subagent**：把范围严格的任务放入独立窗口，取回报告。
- **`/compact`**：压缩当前上下文并据此启动新会话。它是树底的**默认结果**，不是第一选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解有序决策树、五个问题及各分支理由。由于一手来源的成本，应先排除 **Continue**。只在边界作决定；阶段中途要么继续，要么把剩余工作拆给子代理。

## 独立使用

完全位于主流程之外。

- **`$grill-me`**：与 `$grill-with-docs` 相同的持续访谈，但**无状态**，不在本地保存内容，也不创建 `CONTEXT.md`。不在工作目录中处理任务时使用，例如打磨没有仓库承载的计划、设计或文章。工作目录中应使用能留下书面记录的 `$grill-with-docs`。
- **`$grilling`**：访谈原语本身，包括轮次、前沿、由代理查明事实、由用户作出决策。`$grill-me` 和 `$grill-with-docs` 是两个命名入口，`$triage`、`$wayfinder` 和 `$improve-codebase-architecture` 也在内部使用它。只有需要无包装访谈时才直接调用。
- **`$resolving-merge-conflicts`**：逐块处理正在进行的 merge/rebase 冲突，追溯双方一手来源并按**意图**解决，而不是随意选行，随后完成操作。永不运行 `--abort`。已经处于冲突中时独立使用。
- **`$prototype`**：用小型一次性程序回答一个设计问题，例如状态模型是否合理、UI 应该长什么样。一次性约束的是编写方式，不意味着销毁：答案融入真实代码，原型作为**一手来源**保存在 main 之外的 `prototype/<name>` 分支，并由实现 issue 指向。设计问题难以在纸面确定时使用。
- **`$research`**：把阅读跑腿工作委托给**后台代理**；它对照**一手来源**调查，并在仓库留下带引用的 Markdown。调研结果为 `$grill-with-docs` 主流程提供思考材料，不替代思考。
- **`$to-questionnaire`**：阻塞信息存在于**他人**而非用户或代码库中时，为对方编写问卷。它不访谈主题，而是询问发送对象和所需答案，把问题对准知识差距。返回内容供 `$grill-with-docs` 或 `$to-spec` 使用。
- **`$wizard`**：用于只有**人类**能执行的步骤，例如配置基础设施、设置凭据或 CI secret、操作陌生控制台、执行一次性迁移或切换。它生成交互式 Bash，打开 URL、捕获值并写入 `.env` 与 GitHub secrets。代理能自行完成时不要使用。
- **`$wait-what`**：上一条消息未被理解时，在对话或其他 skill 内重新解释，补足上下文，使用简单英语和 `CONTEXT.md` 词汇。
- **`$teach`**：以当前目录作为有状态工作区，通过多次会话学习概念。
- **`$writing-for-agents`**：编写代理读取文档的参考，包括 skill、AGENTS.md 和指针目标文档。

## 前置条件

首次运行工程流程前执行 **`$setup-matt-pocock-skills`**，配置其他 skills 所依赖的 issue 跟踪器、分类标签和文档布局。也支持自定义 issue 跟踪器。
