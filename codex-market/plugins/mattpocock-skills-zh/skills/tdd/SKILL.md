# 测试驱动开发

TDD 是红 → 绿循环。本 skill 说明如何让该循环产出值得长期保留的测试：什么是好测试、测试应放在哪里、反模式以及循环规则。每一节都适用于每轮循环；在循环开始前和进行中查阅，不要事后才看。

探索代码库时，读取 `CONTEXT.md`（如果存在），让测试名称和接口词汇与项目领域语言一致，并遵守所触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底改变，测试不应因此改变。好测试读起来像规格：“用户可以使用有效购物车结账”准确说明系统具备什么能力；因为不关心内部结构，它能经受重构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝——测试放在哪里

**接缝**是执行测试的公共边界：无需进入内部即可观察行为的接口。测试位于接缝，绝不针对内部实现。

**只在预先约定的接缝处测试。** 编写任何测试前，列出要测试的接缝并与用户确认。不要在未经确认的接缝处写测试。无法测试一切；提前约定接缝，才能把测试精力投向关键路径和复杂逻辑，而不是所有边缘情况。

询问：“公共接口是什么？应该测试哪些接缝？”

如果接口本身的形状尚未确定——模块应有多深、接缝应放在哪里、接口应暴露什么——查阅 `$codebase-design` skill 中的词汇。它是“模块、接口、深度、接缝、适配器、杠杆和局部性”等术语的共享来源；把它作为参考查阅，不要把它当成一次独立会话运行。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（例如绕过接口直接查询数据库）。识别信号：行为没有变化，仅重构就让测试失败。
- **同义反复**：断言使用与代码相同的方法重新计算期望值（如 `expect(add(a, b)).toBe(a + b)`、用相同算法手工生成 snapshot、断言常量等于自身），因此测试必然通过，永远无法与代码产生分歧。期望值必须来自独立事实来源，例如已知正确的字面值、完整推导的示例或规格。
- **水平切片**：先写完所有测试，再写全部实现。批量测试验证的是_想象中的_行为：测试事物的_形状_而非用户可见行为，对真实变化不敏感，并在理解实现前就承诺测试结构。改用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是根据上一轮所学调整的**曳光弹**。

## 循环规则

- **先红后绿。** 先写失败测试，再只写足够使其通过的代码。不要预判未来测试，也不要添加推测性功能。
- **每次只做一个切片。** 每轮只处理一个接缝、一个测试和一个最小实现。
- **重构不属于此循环。** 它属于审查阶段（见 `code-review` skill），不属于红 → 绿实现循环。
