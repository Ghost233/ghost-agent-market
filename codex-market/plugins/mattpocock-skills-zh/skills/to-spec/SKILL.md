> **Codex 平台说明：** 本版本使用 `$skill-name` 引用或调用其他 skill；Claude Code 版本使用 `/skill-name`。

此 skill 根据当前对话上下文和对代码库的理解生成规格。**不要**再访谈用户，只综合你已经掌握的信息。

你应该已经获得 issue 跟踪器与分类标签词汇；如果没有，运行 `$setup-matt-pocock-skills`。

## 流程

1. 如果尚未探索仓库，先了解代码库当前状态。规格全文采用项目领域术语表中的词汇，并遵守所触及区域的 ADR。

2. 勾勒用于测试该功能的接缝。优先使用现有接缝，且尽可能选择最高层级。如果必须新增接缝，也要放在所能达到的最高层级。整个代码库中的接缝越少越好，理想数量是一个。

与用户确认这些接缝符合其预期。

3. 使用下方模板编写规格，然后发布到项目 issue 跟踪器。添加 `ready-for-agent` 分类标签，无需额外分类。

<spec-template>

## 问题陈述

从用户视角描述其面临的问题。

## 解决方案

从用户视角描述问题的解决方案。

## 用户故事

一份篇幅充分、带编号的用户故事列表。每条用户故事采用以下格式：

1. 作为<角色>，我希望<功能>，从而<收益>

<user-story-example>
1. 作为手机银行客户，我希望查看账户余额，从而在消费时作出信息更充分的决定
</user-story-example>

用户故事列表必须足够全面，覆盖该功能的所有方面。

## 实现决策

列出已经作出的实现决策，可以包括：

- 将要构建或修改的模块
- 将要修改的模块接口
- 开发者给出的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体文件路径或代码片段，它们可能很快过时。

例外：如果原型生成的片段能比文字更精确地表达某项决策（状态机、reducer、schema、类型形状），可将其内联到相关决策中，并简要注明它来自原型。只保留承载决策的信息，不要放入可运行的演示代码。

## 测试决策

列出已经作出的测试决策，包括：

- 怎样才算好的测试（只测试外部行为，不测试实现细节）
- 将测试哪些模块
- 可借鉴的现有测试（即代码库中同类型的测试）

## 范围之外

描述不属于此规格范围的内容。

## 补充说明

关于该功能的其他说明。

</spec-template>
