# 维护功能知识

调用后直接从当前上下文取证。默认处理当前工作目录，无需用户提供仓库、功能、阶段或参考来源。本 skill 只维护知识文档和必要索引；不实施业务代码、自动提交或发布。

```text
$compile-feature-knowledge 整理当前功能知识。
```

先读取未提交改动和对话记忆，再自行判断功能边界、文档路径、来源与阶段。证据不足以归属任何功能时停止写入并报告缺口，不发起澄清轮次。

## 定位与查询

1. 读取当前仓库的 `AGENTS.md`、`CLAUDE.md`、领域文档和已有功能档案，遵循已有目录约定。
2. 用 `git status --short` 盘点未提交范围，读取 staged、unstaged diff 和相关 untracked 文件；只取证，不修改业务文件。按改动的领域术语、入口、合同和测试识别功能边界；存在多个独立功能时分别维护对应档案。
3. 读取当前对话；宿主提供任务历史或记忆能力时，检索与未提交改动相关的记录。用户已确认的选择是采纳意图，代理提议和未确认讨论只作为缺口，不写成结论。
4. 查找同一功能的现有档案，并复用 `CONTEXT.md`、ADR、spec、合同、测试和 Git 历史。没有现成约定时，首次建立于 `docs/knowledge/features/<功能标识>.md`，并在 `docs/knowledge/` 下维护 OKF bundle；同一功能始终维护同一稳定路径。
5. 需要补足历史因果时，使用当前平台提供的只读探索能力查询功能档案及来源。Codex 可使用 `explorer`，其他平台使用等价的只读子智能体。要求它一次性返回当前结论、关键约束与理由、已替代方案、冲突或缺口，以及具体出处。
6. 重要结论若只存在于当前对话或任务记忆，记录确认日期、结论、理由和“依据本次用户确认”；不要伪造聊天链接或复制完整聊天。

## 证据归类

- 对每条结论独立归类，不要求整次运行只处于一个阶段。
- 当前对话或任务记忆中已确认、但未在代码中落实的方案进入“已采纳但待实施的变更”；新方案替代旧方案时标明替代关系和来源。
- 未提交 diff 能直接证明的实现写入“当前行为”，同时标明尚未提交及实际测试状态；差异本身不等于验收通过。
- 对照 spec 验收条件、测试和审查证据记录验证覆盖范围、版本或 diff、命令与结果；源码核对、测试通过和线上生效分别表述。
- 只移除已落实的待实施事项。部分完成、未验证或与设计不一致的内容保留为限制、偏差或待验证项。
- 旧验证不能为实质变更后的内容背书。没有足够证据时保留缺口，不补写结论。

## 文档内容

按需维护以下章节，空章节不必创建：

- 目标与边界
- 当前行为与关键约束
- 设计理由
- 已采纳但待实施的变更
- 已知限制与设计偏差
- 代码、合同与测试入口
- 验证依据

功能档案负责说明如何维护该功能；协议字段以合同为准，已实现行为以代码和运行证据为准，采纳意图以确认和 ADR 为准。出现冲突时分别记录，不按文件日期自行裁决。

## OKF 0.2

格式的权威定义见 [references/okf-0.2.md](references/okf-0.2.md)；本节为执行摘要，冲突时以规范文件为准。

- 功能概念使用 `type: Feature`，并带 `title`、单句 `description`；按需使用 `tags`。`status` 表示文档生命周期：首次整理用 `draft`，可供消费用 `stable`，保留历史用 `deprecated`，不表示代码是否上线。
- `sources` 为每份外部依据设置稳定 `id` 和真实 `resource`；关键结论以同名脚注归因。普通相对路径按当前文档解析，`/` 开头的链接按 OKF bundle 根解析。
- 仅在实质修改时写入真实的 `generated.by` 和带时区的 `generated.at`。`verified` 只记录实际核验当前文档的人或过程；局部测试不能为全文背书。实质内容改变后，移除不再适用的验证标记，重新核验后再添加。
- 只有存在实际复核期限时才填写 `stale_after`。关联代码、合同或决策变化时重新检查文档。
- `index.md` 和 `log.md` 是保留文件名。bundle 根 `index.md` 可声明 `okf_version: "0.2"`；其他 `index.md` 不带 frontmatter。首次创建功能档案时按需建立或更新索引。

完成前检查 frontmatter 可解析、来源和脚注 ID 对应、受影响索引链接正确，并报告更新内容、验证证据和保留缺口。格式正确只代表结构正确，不代表业务事实已核验。
