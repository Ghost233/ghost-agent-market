# 容器化开发流程

## 适用范围与职责

用户或项目指引已要求容器化开发时，遵循本流程。仓库存在容器构建文件，不足以确立这一要求。

依赖安装、代码生成、编译、测试和服务运行均在容器内执行。宿主机负责源码编辑、检索、Git 操作和容器编排。沿用用户和项目已选定的运行时、工具链和执行入口；运行时操作遵循对应指引。

只运行已有容器程序，且未修改源码或构建输入时，使用项目运行指引核验配置、输入、运行状态和输出。开发阶段按实际需要触发。

面向用户的说明和回复使用中文；用户明确要求其他语言时，按其要求处理。

## 编译任务的三层镜像

需要编译的容器任务采用以下三层。各层可以对应独立镜像或多阶段构建中的阶段，使用项目现有构建入口。

| 层 | 职责和交付内容 | 重建条件 |
|---|---|---|
| 第一层：工具链基础镜像 | 从固定版本或摘要的官方基础镜像派生。保存 Go 等语言工具链、系统编译工具和通用构建工具，不包含当前项目的业务源码。 | 基础镜像、工具链、系统依赖、目标平台或构建配方变化。 |
| 第二层：项目依赖镜像 | 基于第一层，按当前项目的依赖清单完成下载、校验和所需编译。保存可复用的依赖库及其编译结果。 | 第一层内容、依赖清单、锁文件、本地依赖、实际依赖图或影响依赖编译的参数变化。 |
| 第三层：项目编译运行层 | 基于第二层注入本轮源码，完成项目编译、测试和运行，生成日志及业务产物。 | 第二层内容、项目源码或本轮构建、测试、运行输入变化。 |

第二层以项目实际使用的依赖图为准。需要读取源码才能确定依赖图时，将影响依赖选择的输入纳入核验。业务源码变化仅在改变依赖图或依赖编译结果时影响第二层。

Go 的 `go mod download` 只完成下载，不能证明依赖已编译。第二层须保存 `GOMODCACHE`，并预编译实际需要的依赖库，将对应 `GOCACHE` 实际纳入镜像。工具链、目标平台、CGO、构建标签及普通测试或 race 等编译模式须与第三层匹配。无需编译的依赖完成安装和校验即可。仅留在构建器缓存挂载中的内容，不算第二层镜像已交付的依赖。

启动第三层前，核对前两层的输入和内容标识；输入未变时直接复用。源码注入不得覆盖已准备的依赖，正式编译和测试不重复安装同一组已核验依赖。

本机 Apple container 使用 VirtioFS 时，依赖树、编译缓存和编译工作副本放在容器自己的 Linux 文件系统。先用原生复制或归档传入源码，再在容器内展开和执行。宿主绑定挂载用于明确需要持久化的业务数据和小范围输入、输出交换；不要将 `node_modules`、`GOMODCACHE`、`GOCACHE` 等大文件树直接共享给重型安装、编译和测试。启动前检查实际挂载类型，路径名位于容器内不足以证明数据也在容器本地。

## 执行流程

进入下一阶段前，满足当前阶段的完成标准。已有环境和证据有效时，复用它们，从本次变更影响的阶段开始。输入变化时，回到最早受影响的阶段。下文“作业隔离与结果复用”的规则适用于所有阶段，启动作业前先检查。

### 1. 确认环境与执行入口

读取项目容器指引、构建定义和检查入口，确认：

- 实际运行时、执行位置和目标 CPU 架构。
- 工具链、基础镜像、依赖安装方式和构建输入。
- 本次变更影响的模块、共享接口和实际消费方。
- 测试所需的数据库、网络和配置。

核对项目指引、脚本调用与当前运行时。运行时迁移后，先用本次需要的最小路径验证源码注入、依赖访问、命令执行和结果取回。旧说明与实际运行时不符时，按用户已选运行时修正所需入口和对应说明，再验证。

检查构建和运行容器的 DNS，验证本次作业所需的外网域名、内部域名和容器服务名的解析及实际连接。系统默认 DNS 不可用时，通过当前运行时或项目入口显式配置可达的 DNS，例如 `119.29.29.29`、`8.8.8.8` 或 `1.1.1.1`，并保留内部域名解析和容器服务发现能力。配置后重新验证并记录结果；解析成功但连接失败时，继续检查路由、代理和目标服务。

先运行项目最小环境检查，确认执行器和依赖服务可用。环境故障先定位并修复，再执行业务验证。

完成标准：执行入口和环境已明确，最小环境检查通过。环境检查通过只证明执行器可用，业务路径在后续阶段验证。

### 2. 准备依赖并固定输入

首次准备环境、依赖输入变化，或现有依赖环境缺少有效验证时，先准备并核验第一层工具链，再在依赖准备容器内解析、安装和整理依赖。项目设有独立依赖准备容器时，使用该容器；其他项目使用已有入口。

列出受影响模块及其实际消费方。用项目检查确认生产和测试依赖、本地模块引用或替换、清单与锁文件一致。跨仓检查使用与正式构建一致的模块入口和候选组合；被依赖模块自身通过，不能代替消费方验证。

整理产生的清单和锁文件改动须写回源码，再固定输入。构建缓存可用或依赖下载成功，不能代替清单一致性检查。

记录实际参与构建的源码版本、依赖清单和构建配方哈希。未提交改动和未跟踪的构建输入另记录内容哈希。跨仓候选记录各仓库的实际版本组合。每次修改形成新的候选，并重新判断受影响证据的有效性。

完成标准：各受影响模块及实际消费方的依赖检查均通过，清单和锁文件没有待写回变化；实际构建输入已固定，能够区分当前候选。

### 3. 构建并验证项目依赖镜像

依赖准备完成后，按三层镜像约定准备或复用第一层，构建第二层。依赖仍在整理时，继续依赖准备和局部验证，不将候选环境视为已完成的依赖镜像。

分别记录第一层、第二层的输入指纹、内容摘要及父层对应关系。检查依赖库和编译结果实际存在于第二层，并从第二层创建验证容器，确认依赖及其编译结果可供当前项目使用。

构建完成后，核验目标平台、工具链和编译参数。按项目要求完成镜像备份或核验；保存、推送等操作限于当前任务已授权的范围。只有镜像标签不足以证明内容一致。

完成标准：前两层内容和输入可追溯，依赖编译结果已进入第二层，并在新建容器内通过使用核验。

### 4. 注入源码并验证最小业务路径

从已核验的第二层创建第三层临时构建或测试容器，按项目入口注入明确版本的源码。正式编译和门禁使用第二层已准备的依赖；新增或改变依赖时，先返回依赖准备阶段。

先验证受影响模块的编译和最小真实业务路径，再扩展场景。共享接口变化时，记录消费方需要的公共契约候选，包括接口名称、字段、端点和状态规则。

各仓可以独立开发和局部测试。下游最终验收前，固定公共契约及实现候选，所有消费方使用同一版本组合。已启动的作业继续观察并保留结果；候选变化后，按实际影响判断证据是否仍有效。

完成标准：受影响模块能够编译，最小业务路径通过，执行期间没有隐式改变构建输入。

### 5. 定点修复并运行完整门禁

失败后定位首个原始错误，区分产品错误、执行器故障和环境故障。清理异常另行记录，保留原始错误和日志。

测试等待条件须证明本次断言需要的业务状态已到达。例如，验证受控数值变化时，应等待目标样本可用，不能只等待时间戳更新。同类失败再次出现时，检查共同契约、相关调用点和代表边界，先获得能区分原因的定点证据再修复。

先验证失败用例和同类边界，通过后验证受影响模块。收齐已知修复并固定最终候选，再执行项目要求的完整测试和必需检查。

记录实际输入、环境、命令、作业标识、日志位置和真实退出码。超时、取消、跳过和强制清理分别记录，不计为通过。缺少必需检查的有效证据时，将该检查列为未完成。

完成标准：检查覆盖最终候选，业务断言与必需检查均通过，日志和真实退出码可核对。

### 6. 作业隔离与结果复用

并行作业按实际数据库、目录和清理范围隔离。容器名或作业名不同，不证明底层资源独立。必须共用资源时，互斥覆盖采样、业务断言和清理全过程；清理只作用于当前作业拥有的资源。

同一输入、环境、命令及执行范围只保留一个有效作业。不同作业在资源隔离或互斥条件满足时可以并行。观察超时后，先检查原作业状态；确认原作业结束或不存在后，才重新启动。

成功结果仅在输入、环境、验证范围及相关外部条件均未变化时复用。再次重建或重跑完整门禁前，说明变化的输入或条件，以及受影响范围。

完成标准：作业和资源归属明确，没有重复的有效作业；复用证据仍覆盖当前候选与环境。

### 7. 更新产物并记录状态

最终验证通过后，按当前任务和项目要求，从同一固定候选生成业务产物和镜像。源码或构建输入变化后，重新生成受影响产物，并补齐受影响验证。

发布和部署属于当前任务且已获授权时，再执行对应步骤。失败后先核对实际发布或部署状态，再决定后续动作。

完成记录包含：

- 源码候选、构建输入及其哈希。
- 三层镜像或阶段的输入指纹、内容标识和父层关系，以及本次产物的内容标识。
- 验证范围、结果、日志位置和真实退出码。
- 发布、部署的实际状态和未完成项。

完成第三层任务后，先取回并核验日志、真实退出码和产物，再正常停止并删除本轮临时容器。保留可复用的前两层镜像，以及按项目约定持久化的业务数据。需要继续运行的服务按项目生命周期管理。

进度说明已验收范围、当前执行阶段、具体阻断和下一项通过条件。

完成标准：所需产物对应已验证候选，记录可核对。本地验证、镜像发布和实际部署分别报告；本地通过不代表已经上线。
