# Ghost Matt Spec

平台差异：按用户要求，本版先在 Codex 试用并验证；Claude Code / ZCode 保留旧流程，验证后再同步，因此本技能暂仅发布于 Codex。

将当前讨论与代码证据整理为设计规格。本技能独立完成规划，不依赖其他技能的流程。

沿用项目已有规格、领域文档和 tracker 约定；已有文件原位更新，无约定时保存到 `docs/specs/<主题>/spec.md`。规格记录修订、状态和来源，验收项使用稳定编号（如 AC-01）。修订时记录决定变化及受影响工单，不重编号既有条目。

规格状态为草稿、可拆分或需决策；部分就绪时按范围或 AC 标注就绪/阻塞，顶层需决策不阻止独立范围拆分。先交付本地可审阅文档，外部 issue 发布遵循已有授权，不作为规划完成的前置条件。

## 1. 确定范围与现状

读取用户提供的材料、相关实现、领域术语和 ADR，沿关键调用链核对现有能力。复用已确认决定，不重启全面访谈。用户只要求规划时不修改生产代码，也不拆出执行工单或启动开发。

缺失信息可从代码确认的自行确认；影响业务选择的关键问题集中询问，继续完成不依赖答案的部分。不能把未决假设写成已批准合同。

完成条件：问题、目标、非目标、现有行为和决定来源可区分。

## 2. 确定设计与验收合同

明确模块职责与依赖方向，状态/数据的唯一归属；涉及资源时写清创建、共享、取消与释放责任。跨模块说明输入输出、真实入口、认证及公私数据、错误和兼容行为。只填写任务相关约束，不为简单功能创建空泛架构章节。

优先使用现有实现和测试接缝。关键技术假设证据不足时提出或执行已授权的最小验证；不能无依据标为就绪，也不借规划启动完整业务实现或全量测试。跨端功能优先验证一个代表场景的合同可贯通，验证失败回到设计。

为每个外部行为分配验收编号，写清前提/共同事实、实际入口、操作、预期、适用的空数据/来源错误/取消场景、验证层级及依赖。跨端采用共同业务事实，经各端真实协议转换；批准差异单列，不要求身份不同的入口具有相同认证行为。避免所有验证都依赖一个重型 E2E，也不把局部单测冒充跨端证据。

完成条件：相关模块无需各自猜测共享合同；每个范围内目标都有可观察的验收标准。

## 3. 形成规格

按项目约定保存规格，最小结构：

- 修订、状态、来源。
- 问题、目标、范围之外；用户故事仅在帮助说明行为时列出。
- 当前实现与拟议变化。
- 模块职责、跨模块合同及决策依据。
- AC 编号验收矩阵、共同事实与批准差异。
- 依赖、风险、未决决定与必要验证。

文件路径可以作为当前代码证据，不将易变路径当作架构合同；只保留确能表达决定的类型/协议片段。此阶段写逻辑依赖和共享改动，不分配代理或锁死文件清单。

有关键未决项时标为“需决策”并说明影响；已解决时标为“可拆分”。允许不受阻部分明确就绪，但不得让受阻部分进入开发。最终提供规格位置、关键决定与未决事项。仅当用户同时授权拆解时继续任务拆分，否则交付规格即结束。
