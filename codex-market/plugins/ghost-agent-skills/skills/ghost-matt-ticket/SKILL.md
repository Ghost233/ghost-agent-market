# Ghost Matt Ticket

平台差异：按用户要求，本版先在 Codex 试用并验证；Claude Code / ZCode 保留旧流程，验证后再同步，因此本技能暂仅发布于 Codex。

把已确定的规格拆成可执行的任务图。本技能独立完成拆解，不依赖其他技能的流程。

沿用项目现有规格、工单和 tracker 约定，已有文件原位更新。无约定时读取 `docs/specs/<主题>/spec.md`，工单保存到同一主题的 `tickets/<编号>-<标题>.md`，进度索引保存为 `progress.md`。发布或更新外部 issue 遵循已有授权，本地结果可独立交付。

工单采用稳定编号（如 T-01），引用规格修订、合同位置和验收编号（如 AC-01），不复制整段合同。状态区分待办、开发中、开发完成、验收通过和阻塞；开发完成只代表实现与定向检查完成。规格部分就绪时只拆解可确定范围，保留阻塞标记。

## 1. 检查规格

读取规格正文、修订及现有任务，核对相关代码与逻辑依赖。复用已有任务编号，避免重复拆分。没有规格时利用已有明确内容形成可审阅规格草案；设计未确定的部分标阻塞并返回规划，不能边拆任务边臆造合同。

完成条件：本次可拆分范围、受阻范围和合同来源明确。

## 2. 拆解与依赖

优先拆成可独立验证的行为切片，任务大小应能在一次有边界的实施中完成。共享协议、类型、配置或迁移影响多个切片时，指定前置任务和负责范围，下游等待合同稳定；机械性跨仓修改允许统一负责，不强求每张工单贯穿所有层。

为任务声明真实前置条件：共享改动达到什么状态、产物可用且通过哪些最小检查后可开始。避免仅按 UI/API/数据库分层制造大量半成品，也不把无需依赖的任务强制串行。

标明可并行任务与潜在共享文件/构建资源冲突；实际文件写入权由执行前核实。一个逻辑任务需多人合作时指定协调责任，不能让多个代理分别改变同一合同。

每张工单使用以下内容：

- T 编号、标题、规格修订与状态。
- 要交付的行为与范围之外。
- 涉及模块、共享合同引用和潜在修改交集。
- 被哪些任务阻塞，以及解除条件。
- AC 编号、具体交付要求、必要定向检查与正式测试落点。
- 开发完成条件、进入集中验收的条件、已知阻塞。

测试 runner 若缺少继续执行、超时或证据能力，把必要修复显式列为工单，不让执行代理到验收时临时补造整套平台。

## 3. 核对并保存

检查依赖无环、所有引用存在、每个 AC 都有承接任务或明确的共同验收项；共同测试只记录一处。检查并行任务没有未经协调的共享写入，没有遗漏集成行为与正式测试。

保存任务与精简进度索引，说明首批可开始任务、共享前置任务及阻塞项。已有授权和规格足够时直接完成拆分，不要求逐工单确认；拆分暴露设计冲突时回到规格修订。未收到执行授权，不派代理实施。
