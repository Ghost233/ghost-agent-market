# Ghost Matt Implement

平台差异：按用户要求，本版先在 Codex 试用并验证；Claude Code / ZCode 保留旧流程，验证后再同步，因此本技能暂仅发布于 Codex。

每次调用只推进一轮：确定范围 → 开发 → 测试 → 反思审查 → 交付讨论结论并停止。本技能在当前分支、当前工作区独立协调执行，不依赖其他技能的调度流程。进入本轮测试前读取本技能的[整轮测试](references/testing.md)。

沿用项目已有规格、工单和进度位置；无约定时使用 `docs/specs/<主题>/spec.md`、该主题下的 `tickets/` 和 `progress.md`。工单通过稳定编号引用规格修订、合同和 AC 验收项。主线程维护进度中的当前阶段、规格修订、任务状态、文件写入归属、测试轮次与阻塞；状态区分待办、开发中、开发完成、验收通过和阻塞，不将开发完成当作验收通过。

主线程负责总任务与技术决定，常规 Git 操作直接完成。只有独立实现、测试执行或审查能产生有效并行工作时才委派。使用子代理时，调用 `collaboration.spawn_agent`，指定 `agent_type: "worker"`、`model: "gpt-5.6-terra"`、`reasoning_effort: "xhigh"`、`fork_turns: "none"`；宿主无法提供这些参数时说明限制，不静默换模型或声称已经委派。

派发任务提供职责、允许修改范围、规格/工单指针、依赖状态、完成条件、原始证据和升级条件。明确告知代理共享工作区还有其他工作，保留他人修改。普通进度稀疏通信，跨模块冲突和阻塞立即报告。

## 1. 接手并确认边界

读取规格、任务及已有进度，只推进用户授权范围。开始时记录轮次、本轮工单/AC、完成条件和测试范围；优先采用已讨论确定的范围。未指定时从依赖已满足的任务中选择一个最小可验证工单或紧密相关的小组，说明选择，不默认领取全部剩余任务。记录当前分支、各相关仓库 HEAD 与原有未提交/未跟踪改动；确认实际代码仍符合工单依赖。缺少任务时在已有明确规格内补本轮最小任务清单；缺少关键设计时完成无关的安全部分，将受影响任务交回讨论，不能让各代理猜测。

不新建分支、worktree 或临时集成目录替代当前工作区。主线程独占 Git 写操作与进度文档；子代理不切分支、提交、合并、stash、reset、清理或覆盖他人文件。用户已有改动保留并理解后接续；无法安全区分或会覆盖时报告具体冲突。

## 2. 当前工作区并行开发

主线程从依赖已满足的任务中分配不重叠文件/目录的写入归属。同一文件同一时间只有一个写入者；新增越界修改先报告，主线程在原写入者停止后移交或串行处理。共享类型、生成代码、依赖锁文件和配置由指定负责人处理，其消费者待必要检查通过后解锁。

子代理完成本任务实现与正式测试，做必要编译和定向验证；不自行启动全仓验收。共享数据库、构建输出、端口和代码生成会互相影响时由主线程串行安排。代理看到其他任务的半成品导致检查失败，应报告依赖状态，不越界修复。

主线程负责合同决策和阻塞处理。子代理返回改动文件、交付行为、定向结果与剩余问题；主线程核对依赖解除条件，只调度本轮清单内的下游任务。新解锁的范围外工单留待下一轮，不能仅凭“已完成”消息判断。

进入本轮测试前，所有代理停止写入，记录已完成内容、定向检查结果及剩余事项。实现阶段允许为本轮目标做必要调试与定向验证；尚未解决的失败或阻塞如实带入测试与审查，不为追求全绿无限延长本轮。

### 跨模块与重复失败的升级

出现合同冲突、必须修改归属外文件、依赖假设失效，子代理停止相关修改，报告现象、证据、受影响模块及待决定事项。主线程暂停所有受影响的依赖任务，独立任务继续。

同一问题修复后仍复现、同类缺陷出现在第二个模块，或修好一处破坏另一处时，先停止试探性补丁，由主线程检查完整调用链、状态归属、依赖方向和资源生命周期。增加等待、重试、兼容分支不能代替诊断。

区分实现偏离规格、技术合同遗漏或矛盾、业务取舍或范围变化。需要改变架构、合同或本轮范围时，将证据、影响和建议交回讨论，不自行改规格或扩展实施。独立且仍在本轮范围内的工作可继续；阻塞部分记录状态。整体诊断不预设必须重构。

## 3. 本轮测试

按整轮测试约定固定候选，运行本轮 AC 验收和受影响的回归测试。只有用户指定或项目既有门禁要求时才执行全量测试，不因整份规格仍有待办而扩大本轮范围。独立套件继续运行，全部结束或明确阻塞后汇总；测试期间不修改代码、断言、快照或规格。

记录本轮通过、失败、跳过、未运行与阻塞及证据版本。除确认不稳定性、明确环境问题或候选被外部修改所需的有限补验外，不重复整轮。收齐结果后进入反思审查，不自动修复测试失败。

## 4. 反思审查结论

结合测试结果，对本轮起始内容到当前候选的改动进行只读审查，覆盖项目规范、规格符合性、跨模块调用与资源生命周期。可委派独立审查，传完整变更范围和规格指针，不调用带 PR/worktree 前置条件的上游流程。主线程亲自分析证据并按根因分组，不只转述子代理猜测。

明确检查：实现是否偏离要求；测试或环境是否有问题；模块职责、状态归属、依赖方向或合同是否存在架构问题；断言或实现是否属于需求之外的额外功能，以及是否有其他已批准约束支撑。区分已确认原因、置信程度与待验证线索，不预设需要重构，也不把“规格未写”直接判为多余功能。形成最小修改建议、影响范围和后续验证方式，本阶段只给结论，不实施修复。

## 5. 交付本轮结论并等待讨论

报告本轮范围与完成内容、代码版本、测试结果、反思审查发现、建议如何修改及理由、待决定的问题和下一轮候选范围。区分本轮结束、开发完成、验收通过与整份规格完成；剩余工单和未解决问题保留明确状态，不能把本轮通过当作全项目通过。

将进度标为“本轮结束，待讨论”，停止所有本轮子代理写入并结束执行。无论本轮通过或失败，都不自动修复审查发现，不自动启动下一轮；此前笼统的“完成全部开发”或“修复并继续”不取消用户已选择的逐轮讨论节奏。

用户讨论并确认修改方向后，再确定下一轮的工单/修复项、完成条件及测试范围。下一轮可专门修复，也可继续开发；仅询问状态或讨论方案不算启动授权。用户明确说“按此方案执行/继续下一轮”后执行下一轮，完成后仍回到讨论点。

提交和推送仅在已有授权内由主线程执行，显式选择本任务文件，不整体暂存混入其他工作。提交后确认交付内容与验收内容一致。推送后核对涉及本地分支与远端完整 hash；默认只做允许的 fast-forward，同步受未提交文件或分叉阻塞时保留现场并报告，不 stash/reset/rebase。无推送授权时本地交付即可，不虚构远端同步完成。此流程不创建 PR。
