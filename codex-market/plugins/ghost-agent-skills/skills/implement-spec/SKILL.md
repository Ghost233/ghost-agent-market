# 按 Spec 实施

仅在用户显式调用本 skill 并提供 spec 路径或可读取的 issue 时使用。

1. 阅读 spec，以及目标子仓库中距离目标文件最近的 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md` 和相关 ADR。
2. 确认 spec 有明确的验收条件，且不需要新的架构或产品决策；否则留在主线程处理，不派发。
3. 不创建 ticket。在派发前记录当前 `HEAD` 作为审查基线；一次只派发一个会写入工作区的实施子智能体。
4. 启动执行型子智能体。Codex 使用内置 `worker`，任务名设为 `spec_implementer`，模型设为 `gpt-5.6-terra`、推理强度设为 `xhigh`；其他宿主使用等价的实施代理。平台不支持子智能体时停止并说明。只向它提供 spec、负责范围、已确定约束、验收条件和审查基线，并附上以下执行契约：
   - 只实施这一份已批准 spec；不创建或要求 ticket。
   - 开始前读取 spec 和目标范围内最近的代理指引、`CONTEXT.md` 与 ADR。验收条件、依赖、接口或架构决策不明确时，立即返回 `NEEDS_ESCALATION`。
   - 完成可验证的端到端改动，只修改必需文件；不修改需求、架构、`CONTEXT.md` 或 ADR。
   - 在已约定的测试边界优先测试先行，并运行目标仓库要求的类型检查和相关测试。
   - 不启动子智能体，不提交，不推送。
   - spec 对当前会话过大或需要新设计判断时，返回 `NEEDS_ESCALATION` 和最小可独立验证的下一步。
   - 只返回状态（`DONE`、`NEEDS_ESCALATION` 或 `BLOCKED`）、修改文件、验证命令及结果、尚存风险或待决事项；不得宣称整个功能已完成，最终审查和提交由主线程负责。
5. 主线程不得代替子智能体实施代码。等待它返回状态、修改摘要和验证证据。
6. 子智能体返回 `NEEDS_ESCALATION` 或 `BLOCKED` 时，由主线程解决或缩小实施范围；不要创建 ticket，也不要要求它在信息不足时重试。
7. 子智能体返回 `DONE` 后，主线程独立检查 diff、逐条对照 spec 验收条件，并运行适用的验证。当前环境有 `code-review` 时，以第 3 步的基线执行它。
8. 只有主线程完成审查和验证后，才能决定修复、提交或交付。本次工作形成新术语或长期决策时，再由主线程更新 `CONTEXT.md` 或 ADR。
