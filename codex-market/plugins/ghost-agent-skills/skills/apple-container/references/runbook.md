# 执行与验收

## 构建和测试

- 本机镜像构建使用 `container build`。先检查 `container builder status`，需要时启动 builder；构建后用原生容器验证镜像、程序退出码及真实服务。
- 旧版本实测 Apple builder 读取 macOS TMPDIR 存在权限问题。构建上下文优先放在仓库内已忽略的临时目录，包含 Dockerfile 和实际需要的资产；不要把无关目录或凭据加入上下文。
- 按镜像的平台和当前 CLI 帮助显式选择 `linux/arm64`；不能沿用旧 Docker 兼容层默认架构的假设。
- 为编译、测试分配合适的内存。旧项目 Go 编译通常需要约 4 GiB，以项目实际负载与资源限制为准。
- 依赖、测试和服务的执行位置遵循用户要求及项目约定。旧 Socktainer 长 exec 不可靠的结论不约束原生 `container exec`；长任务可作为容器主进程运行，方便记录日志和退出结果。

首次构建、builder 恢复或相关网络变化后，先通过当前 builder 的最小构建步骤验证所需软件源与依赖代理。普通容器请求成功，不能代替 builder 内的验证。沿用项目最小检查入口，已有同环境成功证据仍有效时复用。

## 文件与网络

- 文件传输优先使用原生 `container copy`/`container cp`，先按当前帮助确认方向与参数，并校验输出文件哈希、大小和执行权限。本机 1.5.0 实测原生 copy 的字节往返一致，但 755 文件复制后变为 644；可执行产物须按源文件权限显式恢复并验证。只在实际失败时设计替代通道，不默认使用旧 Socktainer 的 base64 分块绕行。
- 网络故障分别核对 IP 连通性、解析器、域名解析和真实 HTTPS/包仓库请求。区分宿主机、业务容器与 builder 的网络；业务容器的 DNS 配置不能证明构建步骤采用相同配置。
- 多服务项目验证应用实际访问目标的能力；使用 Go 等严格 DNS 客户端时，以应用自身请求为准。

`apk` 索引下载先报 `DNS: transient error` 时，先恢复解析，再判断包名和版本。域名已解析但 HTTPS 连接超时时，检查路由或项目既有依赖代理，并用容器内实际请求验证；不把 DNS 恢复视为依赖仓库已可用。

需要调整 builder DNS 时，先读取当前 `container builder start --help`，核对有效构建作业与归属。确认不会打断其他任务后，再按当前帮助和项目网络设置恢复 builder。故障后先复测失败步骤，通过后接续原流程；不为每次构建固定重启 builder，也不全局修改宿主 DNS。

服务或容器重建后，重新核对地址、解析和连接目标，不沿用旧 IP。状态检查只输出本轮需要的名称、状态、地址、镜像或挂载字段，避免完整输出环境变量。

## 长作业与恢复

同一输入、环境、命令及执行范围的构建、拉取或测试只保留一个有效作业。不同作业在资源隔离或互斥条件满足时可以并行。观察超时或进度停滞时，先核对原作业状态、进度和结果；确认旧作业结束或不存在后才重开。取消与观察超时均不证明底层作业已结束。

需要跨回合继续的作业，把输入标识、容器身份、日志和真实退出结果保存在项目可恢复的位置。记录原作业的接管方法；句柄丢失时查询容器和结果文件，不能直接认定作业已结束。使用 PID 时同时核对启动时间或其他身份信息。

作业恢复后，重新确认依赖服务、网络地址和源码候选。只恢复本次任务拥有的资源，再判断哪些验证证据仍有效。

## 结果

保留真实退出码、日志与业务断言；超时、取消或仅获得产物不能自动记为测试通过。服务启动后检查其实际 HTTP/API 健康端点，不能把进程存在当作业务可用。只有当前源码、镜像和配置实际验证通过，才报告完成。
