# 运行时与 Compose

## 本机与服务器

本机使用 OrbStack 的 Docker 兼容引擎；服务器沿用项目指定的 Docker 端点。使用 `docker context show`、`docker context inspect`、`docker version`、`docker info` 和 `docker compose version` 核对连接目标、客户端与服务端能力；同时核对 `DOCKER_HOST`、`DOCKER_CONTEXT` 等覆盖配置，检查输出仅保留任务需要的字段。

本机目标不符或服务不可用时，先定位当前连接与 OrbStack 状态，按当前任务授权恢复。启动引擎不代表项目服务已经启动。需要 Docker socket/API 的工具使用当前已核验端点；不擅自切换全局 context 或覆盖其他项目的远程连接。

## 项目入口与 Compose

项目容器维护标准 Docker Compose 文件及配套环境配置，固定镜像、命令、环境变量、端口、挂载、网络、运行用户、标签和资源限制。沿用项目现有本机与服务器配置组织方式，执行前用 `docker compose config` 核验；含敏感值的展开配置不直接输出给用户。

- 已声明服务优先使用 `docker compose` 或对应 MCP 编排入口。CLI 或 API 创建的项目容器也须与配置一致。
- 本机持久业务数据使用用户指定目录的绑定挂载。已有卷和数据库文件须保留；迁移前备份，恢复验证后才处理旧副本。依赖缓存按项目开发流程管理。
- 本地测试不要求自动 restart，不为此添加守护进程；常驻服务与服务器按项目生命周期要求配置。
- 按依赖顺序启动后，仍须验证服务就绪及应用实际连接。重建后复验服务名解析、网络与连接目标，不复用旧 IP。

迁移或升级前记录运行中的容器、镜像引用、网络、挂载和需要恢复的服务，保护原有数据并按授权安排停机。迁移后通过项目正式入口验证源码注入、依赖访问、命令执行、结果回收和服务连接。单个 Docker 命令成功不足以证明项目已恢复。

所需入口、数据可见性和服务探活均通过后，才报告迁移完成。后续复用有效证据；运行时、入口或相关网络变化后补验受影响通道。额外宿主机挂载、系统 DNS/路由/防火墙修改、运行时存储迁移及第三方远程构建按当前任务授权执行。
