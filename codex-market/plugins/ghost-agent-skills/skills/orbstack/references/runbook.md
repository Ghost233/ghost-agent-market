# 执行与验收

## 构建和测试

使用项目既有 Docker 构建入口、`docker build` 或 `docker buildx`。先核对实际 builder、目标平台和资源限制；构建上下文仅包含所需源码和资产，排除凭据。平台按交付目标选择，不能从本机架构推断服务器平台。

工具链、依赖层、编译工作副本与增量缓存遵循 `container-dev-workflow`。为编译和测试分配符合实际负载的资源，沿用现有共享 builder 和互斥入口；调整前确认作业归属及影响。

首次构建、builder 恢复或相关网络变化后，通过当前 builder 的最小构建步骤验证所需软件源与依赖代理。普通容器请求成功不能代替 builder 内的验证。已有同环境有效证据时直接复用。

## 文件与网络

- 文件传输使用项目入口或 `docker cp`，核验方向、哈希、大小及执行权限；只在实际失败时设计替代通道。
- 网络故障分别检查宿主机、业务容器与 builder 的 IP 连通性、域名解析和真实 HTTPS/包仓库请求。多服务连接以应用自身请求为准。
- DNS 恢复后复测原失败请求，连接仍失败时继续检查路由和项目依赖代理。修改 builder 网络前确认有效作业及影响，不因每次构建而固定重启 builder 或修改全局宿主 DNS。
- 服务重建后重新核对地址、解析和连接目标。状态检查只输出本轮需要的名称、状态、地址、镜像或挂载字段，避免完整输出环境变量。

## 长作业与恢复

同一输入、环境、命令及执行范围只保留一个有效构建、拉取或测试作业。不同作业按实际资源隔离或互斥。观察超时或停滞时，先核对原作业状态、进度和结果，确认旧作业结束或不存在后再重开；取消或观察超时不证明底层作业已结束。

跨回合作业将输入标识、容器身份、日志、真实退出结果和接管方法保存在项目可恢复的位置。句柄丢失时查询容器和结果文件；使用 PID 时核对启动时间或其他身份信息。恢复后重新确认依赖服务、网络与源码候选，只恢复本任务拥有的资源，再判断已有验证是否仍有效。

## 结果

保留真实退出码、日志与业务断言；超时、取消或仅获得产物不能记为测试通过。服务启动后检查实际 HTTP/API 健康端点，不能把进程存在当作业务可用。取回并核验日志、结果和产物后，再清理本轮临时容器；保留可复用依赖、持久数据和仍需运行的服务。
