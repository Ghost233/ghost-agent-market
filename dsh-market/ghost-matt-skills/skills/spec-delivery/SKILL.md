# Spec 完整交付

这是 DSH 专用版本。用户通过技能选择器调用，也可在允许模型调用时使用 `skill({ name: "spec-delivery" })`。复用当前对话已确认的 spec、工单和授权，缺少影响实施的信息才提问。

本版本使用原生 agent team 的共享 checkout、成员消息和任务板。它取代 `implement-spec` 的独立子代理、每人一个 worktree 和 merger 调度，保留任务图、TDD、阶段审查和总交付要求。

## 建立团队

先确认当前会话具有 Lead 身份，以及 `spawn_teammate`、`send_message`、`list_agents`、`wait_agent` 和四个 `team_task_*` 工具。按宿主实际 schema 调用，继承宿主模型配置。缺少原生 team 能力时，报告缺失项和启用条件，停止依赖团队的开发，不退回普通子代理或单代理实施。

仅 Lead 创建成员。复用已有成员，用 `send_message` 派发后续工作；新成员使用唯一名称。初始任务必须包含 spec 和工单指针、当前阶段、文件归属、验收命令、协作约束和结果回报位置。fresh 成员没有 Lead 的对话；fork 也不包含当前未完成轮次，必要信息须写进任务。

- **Lead**：维护任务图和验收记录，协调文件归属，核对最终 diff，统一执行 Git、集成和 PR 操作。
- **实现成员**：按文件或模块拆分，领取互不重叠的可执行工单，使用 `tdd` 实施并提供验证证据。有多个独立工单和可用成员时，同时推进；有依赖的工单等待前置验收。
- **审查成员**：按 `code-review` 的 Standards 和 Spec 两个轴并行只读审查。Lead 加载该 skill 获取审查方法和报告格式，并把其中的子代理角色映射为 team 成员。实现者不审查自己负责的变更。

成员共享文件系统，写入立即互相可见。每个文件同一时间只有一个写入负责人。成员必须知晓其他成员也在工作，保留他人修改；需要越过归属边界时，先向 Lead 协调。任务板的 `write_scopes` 只提供冲突提示，不是文件锁。格式化、代码生成和测试产物也计入写入范围。

Git 写操作由 Lead 串行执行。成员保持当前分支，不自行暂存、提交、切分支、合并或清理。Lead 在提交、切分支、生成全局产物和固定验收候选前，先收齐相关成员暂停写入的确认。保护用户原有改动；分支或 worktree 的选择遵循项目与用户指引，team 本身不提供隔离。

## 任务调度

用 `team_task_create` 登记工单，写明验收条件、`blocked_by` 和 `write_scopes`。领取或更新前，用 `team_task_list`、`team_task_get` 获取当前状态与 revision，再以 `expected_revision` 更新。遇到旧 revision，重读后重新判断。需要分页时取完任务列表。

实现成员完成修改后，把文件列表、验收结果、日志位置和剩余问题发给 Lead，任务保持待验收。Lead 核对实际 diff 与证据并接收阶段候选后，才以 `complete` 关闭工单。跨阶段依赖指向单独的阶段验收任务；该任务须在阶段审查通过并集成后关闭。任务就绪后，Lead 主动唤醒负责人。

成员消息可用于确认接口、交接和报告阻塞，影响范围、文件归属或验收的决定须同步 Lead 并更新任务记录。发送成功只代表收件箱已接收，不能当作执行或验收结果。

等待前先检查任务板与 `list_agents`。`inactive` 只表示当前没有执行轮次；有未完成任务时，用 `send_message` 唤醒负责人。只有其他必要成员正在运行或创建时，才调用 `wait_agent`；唤醒、超时或 `noProgress` 后重读状态。有独立工单就继续推进。

成员失效时，先确认原执行已停止，再核对保留的修改与验证作业，由 Lead 显式释放或重新分配任务。宿主支持时可用 `interrupt_agent` 停止当前轮次；中断和空闲都不会自动释放任务所有权。恢复执行先核对成员、任务、候选 SHA 和日志，不重复创建仍有效的作业。

## 阶段与总交付

1. **固定验收。** 确定 spec、工单、阶段与总交付起始 SHA、验收条件和项目检查入口。明确阶段 PR → 集成分支、总 PR → 目标分支，两种 PR 的目标须分离。需要真实服务或实机时，先验证最小真实路径；缺口记录证据、负责人、解锁条件和下一动作。
2. **并行实施。** 将当前可执行工单派给实现成员。相交写入范围通过调整归属或依赖串行处理。Lead 验收前置工单并接收候选后，再派发同阶段后继；跨阶段后继等待前置阶段完成交付。
3. **阶段审查与复盘。** 收齐修改、暂停写入并提交阶段候选。提供固定基准 SHA、候选 SHA、规格与标准指针，让审查成员并行审查。随后复盘本阶段的验收遗漏、协作冲突和检查缺口，修复本次范围内确认的 P0/P1/P2；新增需求单列，不扩大原规格。
4. **集中修复与复审。** 同类问题交给同一个实现成员，独立范围可并行修复。两轮仍未关闭的同类问题，使用 `diagnosing-bugs` 建立定点反馈，再继续修复。复审覆盖修复、新变更和受影响路径；只复用基准、候选、规格、标准及覆盖范围仍有效的审查证据。新证据推翻复盘结论时，再补对应部分。
5. **验证候选。** 先运行原始失败用例、同类边界和受影响模块的检查。收齐修复后暂停写入，固定候选，执行项目要求的完整门禁。记录源码 SHA、输入、环境、命令、运行身份、日志和真实退出码。候选或相关条件变化后，补齐受影响验证；同一输入、环境与命令只保留一个有效运行。
6. **完成阶段交付。** 阶段验收满足、已确认 P0/P1/P2 清零且必需检查通过后，创建或更新阶段 PR，在已有授权内合入集成分支。验证合并结果并同步涉及的本地分支，再关闭阶段验收任务、推进后续阶段。需要批准的操作，先把候选和证据准备到可审阅状态。
7. **完成总交付。** 全部 spec 完成后，以总交付起始 SHA 为基准，让审查成员覆盖总 diff 和跨阶段行为；阶段报告仅作输入。修复与验证沿用步骤 4、5。总审查通过后，创建或更新总 PR 并标为 ready；仅在用户明确要求时合并总 PR，随后验证结果并同步本地分支。

在项目既有交付记录中保留一个当前入口，记录阶段、任务 ID、负责人、候选、未关闭问题、有效作业、证据路径和下一动作。区分产品失败、执行器故障、环境阻塞和正常等待；超时、预算耗尽、取消或证据缺失均不算通过。剩余工作全依赖外部条件时，保留未完成任务并报告解锁动作。

全部验收满足、P0/P1/P2 清零、必需检查通过、PR 达到约定状态且本地分支已同步，才报告交付完成。Lead 须等必要成员结果收齐并确认无遗留写入，最终报告 PR、验证结果和剩余问题；总 PR 仅 ready 时注明待合并。
