# UI 原型

在同一路由生成**多个显著不同的 UI 方案**，通过悬浮底栏切换。用户在浏览器中比较方案，选中一个（或组合各方案的部分），然后丢弃其余内容。

如果问题关注逻辑或状态，而不是外观，说明分支选错了；改用 [LOGIC.md](LOGIC.md)。

## 适用情形

- “这个页面应该长什么样？”
- “我想先看看这个 dashboard 的几个方案再决定。”
- “为设置页面尝试不同布局。”
- 用户原本需要花一天在脑中三个模糊 mockup 之间纠结的任何情形。

## 两种子形态——强烈优先选择 A

UI 原型与**应用其他部分紧密相邻**时更容易判断：真实 header、真实 sidebar、真实数据、真实密度。孤立的一次性路由处于真空中，每个方案单独看都不错。只要有合理的现有页面可以承载方案，默认选择子形态 A；只有原型确实没有附近归属时才选择 B。

### 子形态 A——调整现有页面（首选）

路由已经存在。通过 `?variant=` URL 查询参数，在**同一路由**渲染各方案。保留现有数据获取、参数和身份验证，只替换渲染内容。除非有明确理由，否则默认选择此方式。

如果原型对象尚无页面，但*天然应位于某个现有页面内*（dashboard 新区块、设置页新卡片、现有流程新步骤），仍属于子形态 A。把方案挂载到宿主页面中。

### 子形态 B——新页面（最后选择）

只有原型对象确实无法放入任何现有页面时才使用，例如全新的顶层界面，或无法合理嵌入其他位置的流程。

遵循项目现有路由约定创建**一次性路由**，不要新造顶层结构。用名称明确表明它是原型，例如路径或文件名包含 `prototype`。同样使用 `?variant=` 模式。

决定使用 B 前再次确认：真的没有可嵌入的现有页面吗？空白路由会隐藏在内容充实页面中才能暴露的设计问题。

两种子形态使用相同的悬浮底栏。

## 流程

### 1. 明确问题并确定数量 N

默认生成 **3 个方案**。超过 5 个后通常不再显著不同，只会增加噪音，因此上限为 5。

在原型位置或文件顶部注释中，用一行写下计划：

> “在现有 `/settings` 路由提供三个设置页方案，通过 `?variant=` 切换。”

无论用户当前是否在线提出异议，这条说明都有效。

### 2. 生成显著不同的方案

起草每个方案，并遵守：

- 页面目的及可访问的数据。
- 项目组件库或样式系统（TailwindCSS、shadcn、MUI、普通 CSS 等）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

方案必须在**结构上不同**：布局、信息层级和主要操作入口都应不同，而不只是颜色不同。三个略作调整的卡片网格不是 UI 原型，只是壁纸。如果两个草案过于相似，明确要求“不使用卡片网格”并重做其中一个。

### 3. 连接各方案

在路由上创建一个统一切换组件：

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：保留切换器上方的全部现有数据获取逻辑，只让渲染子树随方案变化。

子形态 B（新页面）：在 `/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

在屏幕底部中央放置一个小型固定栏，包含三部分：

- **左箭头**：循环切换到上一个方案。
- **方案标签**：显示当前方案 key；如果方案导出名称，也同时显示，例如 `B — Sidebar layout`。
- **右箭头**：循环切换到下一个方案。

行为：

- 点击箭头更新 URL 查询参数。使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate`，使方案可分享且刷新后保持不变。
- 键盘 `←` 和 `→` 也可循环切换；焦点位于 `<input>`、`<textarea>` 或 `[contenteditable]` 时不要拦截方向键。
- 视觉上与页面明显区分，例如高对比胶囊和轻微阴影，让人一眼看出它不属于正在评估的设计。
- 在生产构建中隐藏。使用 `process.env.NODE_ENV !== 'production'` 或同等检查，避免意外合并原型后向用户发布切换栏。

把切换器写成单个共享组件，供两种子形态复用，并放在项目共享 UI 的现有位置。

### 5. 交给用户

提供 URL 和各 `?variant=` key。用户可以在方便时比较方案。最有价值的反馈通常是**“我想要 B 的 header 和 C 的 sidebar”**，这才是他们真正想要的设计。

### 6. 留存答案并清理

选出获胜方案后，记录选择了哪个方案及原因，再按 [SKILL](SKILL.md) 所述保存原型。把获胜方案融入真实代码，其余方案移到一次性分支，不放入 main：

- **子形态 A**：把获胜方案融入现有页面，从 main 删除落选方案和切换器。
- **子形态 B**：把获胜方案提升为真实路由，从 main 删除一次性路由和切换器。

完整方案集是一手来源，应保存在一次性分支，而不是直接丢弃；但留在 main 的方案组件和切换器会迅速腐化并误导后续读者。

## 反模式

- **方案只在颜色或文案上不同。** 这只是微调，不是原型。真正的方案在结构上意见不同。
- **方案之间共享过多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 会失去比较意义。每个方案都应能自由抛弃现有布局。
- **把方案连接到真实写操作。** 只读原型没有问题。方案需要修改数据时连接 stub；问题是“它应该长什么样”，不是“后端是否工作”。
- **直接把原型提升到生产。** 方案代码在无测试、最少错误处理的原型约束下编写。融入真实产品时要按生产标准重写。
